## 설계 원칙

1. 측정 먼저 한다. 현재 버전의 기준선(F1a grade, F1b 서버 스모크)이 없으면 프롬프트·스킬·모델 변경을 병합하지 않는다.
2. 토큰이 들지 않는 신호부터 쓴다. 채점 순서는 코드 채점기 → 사람 라벨로 보정한 judge → 사람 표본이다. 사실 정확성은 원장 대조 코드로만 판정한다.
3. 새 PR은 신규 서브시스템에만 만든다. 기존 finding은 ID로만 참조하고 앞당김·분할·확장·흡수 관계만 적는다.
4. `merged`는 자주, `published`는 드물게 한다(결정 4). 새 런타임 동작은 D1 settings 기반 기능 스위치로 게시 없이 끌 수 있어야 병합한다.
5. 운영 활성화에는 세 가지가 모두 필요하다. 같은 게이트웨이 스냅샷에서 한 쌍 비교, 대표 승인, 운영자가 지정한 캠페인 staged다. 표본이 작으므로 비율(%) 카나리는 하지 않는다.
6. 보수적 경계를 유지한다. AI 판정은 캠페인을 승인하지 않고 하향만 한다. 사실·진단·외부 행동은 사람이 확정한다. 가중치 학습은 하지 않고, 미확인 비용은 추정하지 않는다.
7. 모델 드리프트는 감시로 막는다. 기반 모델을 별칭 `hermes-agent`로 두므로(결정 10) F2의 보고 모델·게이트웨이 스냅샷 변경 경보가 필수다. 경보가 열리면 F3 활성화와 B3 승격을 동결하고 골든 스모크 재실행 → 재기준선 뒤 해제한다.
8. 공개 저장소에는 스키마, 실패 유형 정의, 합성 fixture, ID, 브랜드를 식별할 수 없는 일반 스킬만 둔다. 골든 입력·라벨·운영 산출물은 D1이나 git이 추적하지 않는 로컬 경로에 둔다. 외부 관측 SaaS로 원문을 보내지 않는다. 새 저장은 records kind로 하고 D1 migration은 0건이다.
9. 새 kind는 F4a kind 레지스트리에 삭제·보존 정책과 함께 등록돼야 병합한다.
10. 평가 실호출은 월 1.5M tokens, 스모크 1회 250k tokens 이하다. 초과하면 대표가 건별로 승인한다(결정 5).
11. 운영자 시간은 주 5시간 이하(운영 3시간, PR 리뷰 2시간)로 설계한다. W1·W2는 예외 주간이다. 병합 PR은 주 평균 1.5개 이하로 둔다.
12. 중단·축소 기준을 둔다. 단계 종료 조건을 채우지 못하면 다음 단계의 신규 에픽을 시작하지 않는다. 용량이 모자라면 B5 GEPA → A5 → A8 → A7 → B4 3부 → A6 순서로 줄인다. 조건부 부분(A5, B5 GEPA, B4 3부)은 W24에 착수 또는 `not_run`을 확정한다.
13. 외부 고객을 받기 전에 필수 게이트를 통과한다. owner 분리 또는 brand ACL, 고객별 데이터 사용 동의, 전역 프롬프트에 고객 원문 금지, 다이제스트·보고서 고객별 분리다. 통과 전에는 내부 브랜드만 다룬다.
14. 위임은 `AGENTS.md` 위임 계약 7항목(`AGENTS.md:46-54`)을 따르고, 각 에픽의 수용 기준을 계약 1항에 옮긴다.

| 스크립트용 운영 쓰기 자격증명 신설 | PR 1·PR 6이 정리 중인 보안 경계를 새로 연다. 레지스트리는 서버가 공개 저장소에서 가져오고 평가는 서버가 실행한다. |
| 사람 채택 전 심층 조사 요약의 자동 주입 | 사람 확정 경계를 바꾸고 외부 텍스트가 모든 역할로 들어가는 경로가 된다. 결정 18과 PR 6 뒤로 둔다. |
| 앱이 원가를 추정하는 기능 | 미확인 비용은 추정하지 않는다. 표준원가는 대표가 확정한 값만 받는다. |
| 밴딧, 계층 베이지안 사전분포, 브랜드 간 사례 은행 | 표본이 작고 지점·브랜드 간 일반화 금지가 설계다. 동의와 비식별화 규칙이 먼저다. |
| 외부 관측 SaaS로 원문 전송 | 고객 브랜드 원문이 외부로 나간다. D1 자체 원장(F2)으로 충분하다. |
| 벡터 DB·RAG | 자료가 브랜드당 200개 이하다(`app/api/archive/route.ts:30`). 맥락 선택은 B5 리플레이로 먼저 고른다. |
| 요청 단위 역할별 모델 라우팅 | HERMES 요청에 모델·도구·max_tokens 지정이 없고(`lib/hermes.ts:25-29`) 도구 구성은 서버 전체 공통이다(`server/research-worker/install.py:116`). 게이트웨이 지원 확인이 먼저다. |
| Workers cron·Workflows 전환 | 배포 환경 지원이 확인되지 않았다. 워커 tick 큐로 대신한다. |
| 경쟁사·트렌드 주기 모니터링 | 조사가 이미 토큰의 87%를 쓴다. `loop-4` 예산과 PR 6 브라우저 격리가 먼저다. |
| 멀티 테넌트 고객 포털과 외부 고객 온보딩 | 현재 고객은 내부 브랜드뿐이고 운영 계정은 1개다. 외부 고객 수주 전 필수 게이트를 통과한 뒤 따로 계획한다(결정 14). |
| 차단 우회(주거용 프록시, 로그인 세션)와 MMM | 보안 경계(PR 6)와 플랫폼 정책 결정이 먼저다. MMM 대신 incrementality-lite(A4)를 쓴다. |
| 기존 finding 재계획과 제외 항목 재개 | 기존 finding은 ID로만 참조한다. `data-truth-11`은 권고 (1)만 F4a에서 다시 열고, 나머지 제외 항목은 기존 결정을 따른다. |

## 열린 질문

1. HERMES run 응답에 실제 기반 모델과 토큰이 항상 오는가? 별칭을 유지하므로(결정 10) F2 드리프트 감시가 무엇을 볼 수 있는지가 여기에 달려 있다.
2. HERMES가 세션을 넘어 메모리나 스킬을 축적하는가? 그렇다면 F1b 서버 평가와 B5가 운영 에이전트 기억을 오염시킬 수 있어 평가 전용 프로필이 필요하다.
3. Workers에서 공개 저장소 raw 경로를 가져올 수 있는가? 캐시 지연은 얼마인가? F3 등록 방식의 전제다.
4. Sites에서 직전 버전으로 되돌리는 절차가 있는가, 아니면 직전 제품 커밋 재게시(약 18분)만 가능한가?
5. 게시 1회의 실제 크레딧 소모량과 주간 한도는 얼마인가? 묶음 주기와 예비 핫픽스를 확정하는 데 필요하다.
6. 운영 D1을 읽기 전용으로 직접 조회할 수 있는가? 없다면 W1 기준선 가운데 새 읽기 API와 게시가 필요한 항목은 무엇인가?
7. 운영 Workers CPU 한도는 얼마인가? 저장 직후 온라인 채점과 서버 평가 채점을 요청 안에서 감당할 수 있는가?
8. ODA C107 오픈은 상대 몇 주차인가? ODA 캠페인은 storeId로 지점에 연결돼 있었는가? 결정 13 분기가 여기에 달려 있다.
9. 점포 POS 내보내기에 적립 고객 ID와 쿠폰 코드 열이 있는가? 배달앱 정산 자료에 수수료 항목이 따로 나오는가?
10. 브랜드·지점별로 성과 채널 계정이 따로 있는가? F5의 자격증명 단위가 달라진다.
11. 커머스 브랜드의 실제 판매 채널과 주문 내보내기 형식은 무엇인가? 필요하면 north-star를 커머스로 넓히는 후보 에픽이 된다.
12. 1인 운영에서 월 몇 건의 사람 라벨이 나오는가? κ 30건, 교정 5건 문턱에 언제 도달하는가?
13. 9/17 완주와 9/23 재질문의 차이는 모델 변경, 입력 증가, 과업 필드 부재 중 무엇 때문인가? 9/17 제출 원문으로 F1b에서 정확히 리플레이할 수 있는가?
14. Buffer가 게시 뒤 Instagram 게시물 ID를 돌려주는가? B4 저장·공유 지표와 `loop-2` 연결의 전제다.
15. 코딩 레인 2개, PR 6 전담 1개, 대표 주 2시간 리뷰라는 가정이 현실적인가?
