# 화면·UX 평가와 개선 개발 계획 (UX 2차)

작성: 2026-10-01, Claude 세션(대표 지시 "콜렉티브 앱을 UI/UX 측면에서 최고 수준의 솔루션 기준으로 평가하고 향후 개선안에 대한 개발 계획을 깊게 수립하라"). 평가 대상은 현재 운영 Sites 82 = main `aea167d`(tree `035d3b1`)이다. 이 문서는 **제안**이며 대표 결정 전에는 구현을 시작하지 않는다. 구현 소유는 [레인 표](LANES.ko.md)의 A(제품 기능)이고, 레인 분할은 [10절](#10-일정레인병행-전략)에서 제안한다. 2026-09-23 UX 1차(`ux-1`~`ux-12`, [개선 계획](IMPROVEMENT-PLAN.ko.md) PR 5)는 라우팅·정합성·권한 반영이 목적이었고 모두 반영됐다. 이번 2차는 정보구조·작업 흐름·디자인 체계·접근성·성능·문장을 다룬다.

## 0. 한 장 요약

- **총평 2.3 / 5.** 기능 깊이와 상태의 정직함(미확인·보류·실행하지 않음)은 최고 수준 제품에도 드문 강점이다. 그러나 제품이 "지금 무엇을 해야 하는지"를 알려주지 않고, 사용자가 27개 접힘 패널과 9+5+15개 탭 사이에서 흐름을 스스로 찾아야 한다. 핵심 작업 흐름(시장 근거 → 고객·기회 → 상품 → 오퍼 → 미션)의 편집기는 성장·판매 탭 **맨 아래**에 있다.
- **계측 수치(현재):** 성장·판매 탭을 열면 GET 31건이 한꺼번에 나가고 접힌 상태로도 데스크톱 3,366px(4.2화면)·모바일 4,517px(5.4화면)이다. 첫 로드 JS 2.1MB(메인 청크 압축 388KB), CSS 252KB. axe(WCAG 2.x AA) 색 대비 위반 1,249노드(46개 캡처 합계), 44px 터치 타깃 충족 약 5%, 성장 패널 설명문 7.9천 자, '새로고침' 버튼 라벨 35종, '저장' 계열 동사 6종.
- **목표:** 12차원 평균 2.3 → 4.0. 7단계(P0~P6, 선택 P7) 약 11~12주(레인 1개) 또는 7~8주(위생·구조 2레인 병행). 외부 실행·서버 의미·상태 어휘는 바꾸지 않는다.
- **대표 결정 6가지:** [12절](#12-대표-결정-필요-사항). 핵심은 성장·판매 탭 6섹션 재구성 승인과 홈을 '오늘의 안건' 중심으로 바꾸는 것이다.

## 5. 화면별 소견

- **홈(워크스페이스):** 첫 화면 400px가 히어로("어떤 성장을 만들고 싶으신가요?")다. 재방문 운영자에게는 매일 같은 광고다. 지표 4개 중 2개(브랜드 4·AI 전문가 8)는 상수다. "AI 팀 8" 배지는 알림처럼 보이지만 상수다. 결정 대기(위임 승인·확대·최적화 채택·상세페이지 승인·협업 승인)·기한(문의 약속·미션·협업 납품)·신호(감지·재고 일수)·일일 루프 결과가 홈에 없다.
- **캠페인 목록:** 표 자체는 명료하다. 모바일에서 열 6개가 가로 스크롤로 잘린다(캡처 mobile-01). 행 메뉴 '⋯'가 32px.
- **캠페인 상세(시트):** 제목 아래 설명이 "전략에서 검수까지, 하나의 캠페인으로 연결합니다"라는 고정 문장이다(정보 0). 작업 영역이 겹침 시트라 뒤 목록이 흐려진 채 남고, 주소·새로고침·공유가 브리프로 떨어진다. 시트 안 9탭은 모바일에서 "Meta 광고 ɛ"로 잘린다.
- **성장·판매 탭:** 순서가 (1) 헤더 + 새로고침 (2) **전역 실행 중단**(계정 전체 영향, 긴 설명 2문단, "기록 없음 · v0") (3) 개인정보 경고 (4) Meta 열기 버튼 (5) 주문 장부 카드(미확인 4개) (6) 접힘 패널 27개 (7) **그제야** 작업 단계 탭(시장 근거→미션)과 편집기. 사용자가 상품을 등록하려면 4~5화면을 내려가야 한다. 패널 요약은 기본 삼각형과 텍스트뿐이라 상태·건수·기한이 없다. 열면 안의 h3가 다른 문구로 다시 나오고, 각 패널에 "<X> 새로고침" 버튼이 따로 있다.
- **Meta 광고 준비:** 4단계 스텝(판매 목표 0/2 → 준비 점검 0/8)과 "계획 미리보기 0/22"는 이 제품에서 가장 잘 설계된 흐름이다. 다만 위에 15개 하위 탭이 두 줄로 겹쳐 스텝과 경쟁한다. 이 스텝 패턴이 성장·판매 탭의 모델이 돼야 한다.
- **제작·발행:** 단계 칩(사실 확정 → PNG → 채널 → 한도 → 초안 → 승인 → 접수)이 흐름을 보여주지만 칩이 눌리지 않고, 섹션마다 설명 2~3줄이 먼저 온다.
- **연결 및 설정:** 7화면 길이, 32행 기능표, 비밀값 입력 폼 3개가 한 페이지. 설정은 좌측 하위 메뉴(연결·수집·비용·기능표)로 나눠야 한다. critical 2건(`aria-valid-attr-value`)이 여기 있다.
- **브랜드 아카이브:** 4단계 진행 표시와 "근거 준비 상태 0/7"은 좋다. 그러나 버튼 7개가 한 줄에 나열되고(인터뷰·심층 조사·자료 추가·분류·브리프·점포), 탭 7개가 또 아래에 있다. 지표 카드 8개가 모두 "미수집"으로 첫 화면을 채운다 — 빈 상태는 한 카드로 접어야 한다.
- **점포 마케팅:** 목표 카드·4지표·6과제 카드·탭 6개. 구조는 좋다. 과제 카드의 "확인·기록" 버튼이 32px이고 "미확인" 배지가 대비 미달이다.
- **바이럴 학습:** 히어로 + 4지표 + 4탭 + 빈 상태. 홈과 같은 '광고형' 첫 화면 패턴이 반복된다.

## 6. 지켜야 할 강점

1. **정직한 상태 어휘**(미확인·보류·실행하지 않음·운영자 확인)와 null을 0으로 바꾸지 않는 원칙. 벤치마크 제품들도 못 지키는 부분이다. 개선안 전체가 이 원칙을 보존해야 한다.
2. **입력 보존·요청 ID 재시도·버전 충돌 감지**(CAS). 구현이 21곳에 복제됐을 뿐 설계는 옳다.
3. **URL 복원**(화면·브랜드·지점·일부 탭)과 뒤로가기 동작, 없는 id 교정.
4. **E2E 60개·단위 295개**가 화면 동작을 잠근다. 재구성 비용은 크지만 안전망이 있다.
5. **Meta 준비 스텝**과 **점포 6과제 카드**: 이미 있는 좋은 패턴.
6. 팔레트·로고·여백의 브랜드 감각. 바꿀 것은 체계이지 취향이 아니다.
7. 패널별 오류 경계(`app/growth-panel-boundary.tsx`)와 가로 넘침 E2E 검사.

## 7. 목표 경험과 설계 원칙

### 원칙
1. **오늘 결정할 것이 먼저.** 홈과 각 캠페인의 첫 화면은 결정 대기·기한·이상 신호다. 환영 문구는 첫 사용자에게만.
2. **한 화면 한 작업.** 섹션 하나가 열리면 다른 섹션은 요약 한 줄로 접힌다. 접힘 패널 27개를 한 번에 그리지 않는다.
3. **모든 위치에 주소.** 탭·섹션·패널·기록 id가 URL에 있다. 공유·새로고침·뒤로가기가 같은 자리로 온다.
4. **상태는 색이 아니라 말로, 말은 한 문장으로.** 안내는 ≤60자 한 문장, 나머지는 '자세히'. 상태어는 [AGENTS 어휘](../AGENTS.md)에 맞춘 사전 한 벌.
5. **기계 형식 비노출.** ISO·ms·enum·내부 ID는 포맷 함수와 라벨 맵을 거친다. ID는 복사 버튼 뒤에.
6. **실패는 자리에서.** 필드 오류는 필드 아래, 충돌은 선택지 2개(내 입력 유지 / 서버 값 보기), 성공은 초록 한 줄.
7. **손가락 기준.** 모든 타깃 ≥44px, 표는 768px 아래에서 카드, 시트는 페이지.
8. **빠르게 느끼게.** 섹션 열기 ≤3요청·골격 로딩, 재방문은 캐시, 초기 JS ≤150KB gz.
9. **위험은 자기 자리에.** 계정 전체 중단은 설정과 상단 배지에, 캠페인 화면에는 "중단 중" 띠만.
10. **기존 경계 유지.** `mayExecute:false`, CAS, 요청 ID, 권한 판정, 삭제 보호를 그대로 둔다. UI 재구성은 서버 의미를 바꾸지 않는다.

## 11. 위험과 경계

- **E2E 60개 중 35개가 성장 탭 로케이터(summary 문구)에 의존.** P1·P2는 summary 문구를 유지하고, P4에서 섹션 내비 기준으로 한 번에 바꾼다.
- **공통 훅으로 옮기며 CAS·멱등 회귀.** 서버 route 테스트 15개가 계약을 잠그고, 훅 단위 테스트를 추가한다. 요청 ID는 지금처럼 UUID v4, 디제스트 충돌 409 유지.
- **성장2 원안 추적 문서와의 어긋남.** 패널 이름이 바뀌면 [원안 추적](GROWTH-2-PLAN.ko.md)의 문서 링크는 유지하고 화면 이름만 갱신한다.
- **집계 API 비용.** `/api/growth/summary`·`/api/agenda`는 카운트와 최신 1건만 돌려주고, 상세는 섹션을 열 때 읽는다. Workers CPU 한도 감시는 게시 뒤 24~72시간 규칙을 따른다.
- **이 계획이 하지 않는 것:** 외부 실행·발행·지출·고객 발송 추가, 서버 의미·권한 변경, 상태 어휘 변경, 실계정 검증. 홈 안건은 집계이지 자동 집행이 아니다.
