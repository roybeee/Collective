# 셀프 가입 (G8)

셀프 가입은 무인 키오스크에서 회원 카드를 직접 만드는 것과 비슷하다. 지금까지는 직원(관리자)이 카드를 만들어 건네줬다(초대 링크). 스위치를 켜면 손님이 스스로 새 워크스페이스를 만들 수 있다. 끄면 예전처럼 초대로만 들어온다.

기술적으로는 `AUTH_MODE=email`에서 `POST /api/auth/signup`이 확인 대기 계정과 24시간 일회용 확인 링크를 만들고, 확인하면 자기 id를 `workspace_owner`로 갖는 새 워크스페이스의 소유자로 로그인시킨다.

## 스위치

- `self_signup`(기본 꺼짐). 플랫폼 스위치다: 운영자 워크스페이스(가장 먼저 만든 관리자 계정의 `workspace_owner`) 값만 읽는다. 다른 워크스페이스에서 켜도 열리지 않는다.
- 꺼져 있거나 이메일 모드가 아니면 `GET /api/auth/signup`은 `enabled:false`, `POST`는 404다. 로그인 화면에 가입 버튼이 없고 초대·재설정·bootstrap·로그인은 이전과 같다.
- 다시 끄면 새 가입·확인은 404이고 이미 가입한 계정의 로그인은 그대로다.

## 흐름

1. 로그인 화면의 '새 워크스페이스 만들기(가입)'(스위치 켜짐일 때만). 이메일, 비밀번호(기존 정책 12~128자, `autocomplete` new-password·username으로 비밀번호 관리자 허용), 동의 3개.
2. 동의: (필수) 이용약관, (필수) 개인정보 수집·이용, (선택) 마케팅 정보 수신. 세 칸 모두 처음에는 비어 있다. 서버는 두 필수 값이 정확히 `true`가 아니면 400이다. 마케팅은 boolean만 받는다. 동의 기록은 새 워크스페이스의 `signup_consent` 1행(문서 판 `terms-draft-2026-11`·`privacy-draft-2026-11`, 마케팅 여부, 시각)이다.
3. `action:'start'`: 계정 `auth_users`(role admin, status pending, workspace_owner = 자기 id, 비밀번호 scrypt 해시)와 `auth_tokens`(kind `verify`, 해시만 저장, 24시간)를 만든다. `workspace_origin` 1행을 남겨 예시 브랜드·캠페인을 넣지 않게 한다(`lib/server.ts` `seedBrands`).
4. `action:'verify' {email, token}`: 링크 일회 소비·계정 활성화·세션 생성을 한 batch로 한다. 이메일이 다르거나 만료·사용·폐기된 링크는 401. 확인 뒤 빈 워크스페이스(브랜드 0, 캠페인 0)로 들어간다.
5. 확인 전에는 로그인할 수 없다(401). 확인 전 같은 이메일로 다시 가입하면 새 비밀번호·새 링크로 바꾸고 이전 링크를 폐기한다.

거절: 이미 활성인 계정 이메일, 초대 대기 이메일(다른 워크스페이스 소속), 확인을 마친 이메일은 409다. 확인 토큰은 초대 수락(`accept`)에 쓸 수 없다.

## 메일 발송(중요)

초대 링크와 같은 방식을 따른다. 이 판에는 메일 발송 어댑터가 없어(초대·재설정 링크도 관리자가 직접 전달) **확인 링크를 가입 화면에 그대로 보여 준다**(`delivery:'display'`). 따라서 지금은 이메일 소유권을 검증하지 못한다. 다른 사람의 이메일로 가입할 수 있다.

공개 운영 전 필요한 일(대표 결정 후):

- 메일 발송 연결(트랜잭션 메일 서비스), 응답에서 `verifyUrl` 제거, 링크는 메일로만 전달
- 이용약관·개인정보 처리방침 확정본 공개와 문서 판 갱신, 마케팅 수신 동의(정보통신망법 제50조) 철회 경로
- 회원 탈퇴(워크스페이스 삭제) 경로를 가입만큼 쉽게
- 가입 남용 관찰(가입 수·IP), 필요하면 CAPTCHA가 아닌 방식(이메일 확인·요청 제한·지연)으로 보강

## 보안·접근성

- 요청 제한은 로그인과 같은 `auth_rate_limits`: IP 100회, 이메일+IP 10회, 이메일 전체 50회 초과 시 점진 지연(15분 창). 거절된 입력도 센다.
- CAPTCHA·퍼즐은 쓰지 않는다(WCAG 2.2 3.3.8 접근 가능한 인증). 비밀번호 붙여넣기·관리자 자동완성을 막지 않는다.
- 같은 출처(Origin)·JSON 요청만 받는다(`authBody`). 세션 쿠키·만료는 기존 이메일 인증과 같다(`lib/auth-session.ts`는 바꾸지 않음).
- 새 소유자는 자기 워크스페이스의 기능 스위치를 바꿀 수 있다(기존 소유자 권한). 플랫폼 스위치(`self_signup`·`credit_billing`)는 운영자 값만 읽으므로 영향이 없다.
