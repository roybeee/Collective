# 상품 리서치·MD 에이전트 개발 계획 (PR 계획 v1)

결론: COLLECTIVE 안에 **판매할 상품을 스스로 찾고, 객관 지표로 평가하고, 근거와 함께 선정안을 올리는 MD 에이전트**를 만든다. 공식 API와 계약 데이터로 수집하고, 설명 가능한 점수표로 평가한다. 선정안은 이미 있는 성장2 흐름(시장 신호 → 소싱 후보 → 카탈로그 → 오퍼 → 미션 → 성과)에 그대로 꽂는다. 목표는 아래 12차원 기준 평균 **4.7/5 이상**이고, 모든 차원 4.5 이상이다. 기간은 개발 약 10~12주에 예측력 관측 기간을 더해 잡는다.

- 지시: 대표(2026-10-03) "판매할 물품을 자동으로 조사하고, 평가하고, 선정하는 에이전트를 개발해서 collective와 연결… 업계 최고 수준… 5점 만점에 4.7점 이상".
- 작성: Claude 세션(성장2 인계 소유). 이 문서는 **계획**이며, 구현은 대표 승인(10절) 뒤 시작한다.
- 범위 구분: [성장1 종료 문서](GROWTH-1-CLOSEOUT.ko.md)는 '상품 MD'를 성장2 범위로 정한다. 이 기능은 성장1 종료 조건에 더하지 않는다.

비유: 지금 COLLECTIVE는 "무엇을 팔지 정해 주면 잘 파는" 팀이다. 이번에는 매일 아침 시장을 돌아보고 "이번 주에 이 다섯 개를 들여오자, 근거는 이것"이라고 보고하는 MD를 붙인다. 이 MD는 들여오기(발주)를 직접 하지 않는다. 대표가 승인하면 소싱 검토로 넘긴다.

## 1. 지금 있는 것과 빈 곳

| 영역 | 지금 있는 것(파일) | 빈 곳 |
|---|---|---|
| 시장 신호 | `growth_signal`, 확정 시장자료 가져오기(`lib/growth-signal-source.ts`), 출처 계보와 하위 보류 전파 | 외부 지표를 **자동으로** 모으는 수집기가 없다. 사람이 등록한 자료만 신호가 된다 |
| 기회 탐지 | `lib/growth-detection.ts`: 자사 주문·재고·반품 고정 규칙 | 외부 시장 지표 규칙이 없다. 예측도 하지 않는다(`isForecast:false`) |
| 소싱 | `growth_sourcing_candidate`(원가·MOQ·납기·견적 유효기한), 비교안, `mayOrder:false` | 후보를 **찾는** 단계가 없다. 이미 정한 상품의 견적만 비교한다 |
| 카탈로그·오퍼·미션 | `growth_catalog`, `growth_offer`, 미션, 재고 원장, 재발주 | 선정 근거와 카탈로그를 잇는 연결이 없다 |
| 웹 조사 | 조사 작업자(Hetzner 서버 + HERMES web_search/extract), 도구 등급 정책 | robots.txt·약관·호출 속도 정책이 **없다** |
| 외부 연결 | `lib/connectors/naver-ads.ts`(검색광고 API, HMAC 서명, 캠페인·통계만), 자격증명 암호화 저장 | 키워드 도구(`/keywordstool`), 데이터랩, YouTube, 쿠팡 연결이 없다 |
| AI 팀 | 8개 역할(`lib/agency.ts`), 실행·작업물 판·승인 | 상품 리서처/MD 역할이 없다 |
| 평가 | 결정형 채점기 15개, 판사 루브릭(1~5), 카파 보정(레인 Q) | 상품 선정의 **예측력**을 재는 백테스트가 없다 |
| 일정 실행 | 작업자 틱 큐(`growth_daily` 등), 하루 1회 루프 | 상품 리서치 큐가 없다 |

정리하면, 판매·실행 쪽 뼈대는 충분하다. 빠진 것은 앞단의 **수집 → 정규화 → 평가 → 선정** 네 단계와, 그 결과가 맞았는지 재는 **검증 장치**다.

## 2. 평가 기준: 12차원 루브릭 (목표 평균 4.7)

UX 3차와 같은 방식으로 독립 평가자가 매 단계 채점한다. 차원마다 4점·5점 조건을 미리 정하고, 숫자로 확인할 수 있는 조건만 둔다.

| # | 차원 | 4점 조건 | 5점 조건 |
|---|---|---|---|
| ① | 데이터 커버리지 | 공식 API 4종(네이버 검색광고 키워드·데이터랩·네이버 쇼핑 검색·YouTube) 상시 수집, 대상 카테고리 3개 | 위 + 랭킹 출처 3종(쿠팡·무신사·올리브영)을 계약 데이터 또는 운영자 가져오기로 주 1회 이상 확보, 자사 판매·발행 관측 결합 |
| ② | 데이터 신선도·신뢰성 | 출처별 수집 주기·최종 수집 시각 표시, 결측은 '미확인'(0 아님), 원본 스냅샷 해시 보존 | 수집 성공률 ≥ 98%(30일), 이상치 자동 격리, 모든 숫자에서 원본 스냅샷까지 한 번에 이동 |
| ③ | 수요 측정 정확도 | 키워드 절대 검색량(검색광고) + 상대 추세(데이터랩) 결합 | 데이터랩 상대값을 절대량으로 보정한 월별 추정의 오차 ≤ 15%(검색광고 실측 대비), 연관 키워드 묶음 단위 수요 |
| ④ | 트렌드 예측력 | 과거 데이터 백테스트 하네스, 기준선(현재 1위·단순 모멘텀) 대비 보고 | 12주 백테스트에서 '상승 후보' 정밀도@20 ≥ 0.45 **그리고** 최고 기준선보다 +15%p 이상, 후보 ≥ 200건 |
| ⑤ | 경쟁·시장 구조 | 판매자 수·상위 상품 리뷰 수·광고 경쟁 지수 표시 | 가격대 분포·신규 진입 속도·상위 집중도로 '비어 있는 자리'를 설명, 경쟁 점수와 실제 진입 난이도의 순위 상관 ≥ 0.5 |
| ⑥ | 수익성·실행 가능성 | 판매가 대비 원가·배송·수수료로 예상 공헌이익 계산(소싱 후보와 연결) | 채널별 수수료표·MOQ·납기·재고 회전까지 넣은 손익 시뮬레이터, 출시 상품의 실제 공헌이익 오차 ≤ 20% |
| ⑦ | 리스크·규제 판단 | 식품·화장품·KC 인증·상표 리스크 체크리스트 | 규제 체크 누락 0(감사 표본 50건), 가품·상표 분쟁 신호 탐지, 고위험은 자동 선정 금지 |
| ⑧ | 브랜드 적합성 | 브랜드 사실(브랜드 아카이브)과 대조한 적합성 메모 | 대표·MD가 매긴 적합성과 일치율 ≥ 80%(블라인드 50건) |
| ⑨ | 설명 가능성·근거 | 선정 메모의 모든 숫자에 출처 인용 | 인용 정확도 100%(자동 채점기), 근거 없는 주장 0, 점수 분해(왜 이 점수인가) 한 화면 |
| ⑩ | 의사결정 연결 | 선정안 → 시장 신호·소싱 후보 초안 자동 생성 | 승인 1회로 소싱 → 카탈로그 → 오퍼 초안까지, 출시 뒤 성과가 점수 가중치 보정에 되돌아옴 |
| ⑪ | 자동화·운영 효율 | 매일 자동 수집·채점, 주간 MD 리포트 자동 작성 | 대표의 주간 검토 시간 ≤ 30분, 쿼터·비용 예산 안에서 100% 운영(초과 0), 실패 자동 재시도·알림 |
| ⑫ | 컴플라이언스·안전 | 출처 레지스트리(허용 방식 api·licensed·manual), robots.txt·약관 위반 수집 0 | 법무 검토 완료, 개인정보 저장 0(집계만), 전역 중단·기능 스위치·승인 관문 E2E 통과 |

평균 4.7이 되려면 합이 56.4 이상이어야 한다. 예: 5점 6개 + 4.5점 6개 = 57/12 = 4.75. **4.5 미만 차원이 하나라도 있으면 목표 미달**로 본다.

외부 비교 기준(업계 수준): 아이템스카우트·판다랭크 같은 셀러 분석 도구는 키워드 검색량·경쟁도·랭킹 추적을 준다. 이 계획은 그 위에 ④ 예측력 검증, ⑥ 우리 원가·재고와의 손익 연결, ⑩ 실제 판매 결과의 학습 반영을 더해 차별화한다. 이 세 가지가 '업계 최고'의 근거가 되도록 5점 조건에 숫자로 묶었다.

## 3. 데이터 출처와 수집 방식

원칙은 **공식 API → 계약 데이터 → 운영자 가져오기** 순이다. 사이트를 몰래 긁는 수집은 하지 않는다.

| 출처 | 얻는 것 | 방식 | 한도·제약 | 판정 |
|---|---|---|---|---|
| 네이버 검색광고 API `/keywordstool` | 키워드 월간 검색수(PC·모바일), 연관 키워드, 경쟁 지수 | 기존 `naver-ads` 연결에 읽기 경로 추가 | 광고주 계정·API 키 필요, 호출 속도 제한 | 공식, 1순위 |
| 네이버 데이터랩 검색어 트렌드·쇼핑인사이트 | 기간별 상대 추세, 쇼핑 카테고리 클릭 추세, 성별·연령 | 개발자센터 키 | 하루 1,000회 수준, **상대값만** 준다 | 공식. 검색광고 절대값으로 보정 |
| 네이버 검색 API(쇼핑) | 상품 수, 최저가, 판매처 분포 | 개발자센터 키 | 일일 쿼터 | 공식. 경쟁·가격대 분석 |
| YouTube Data API v3 | 영상 조회수·증가 속도, 채널 구독자, 관련 영상 수 | API 키 | 하루 10,000 단위. `search.list` 100단위, `videos.list` 1단위 | 공식. 검색은 아끼고 영상 단위 추적 중심 |
| 쿠팡 파트너스 API | 카테고리 베스트, 상품 검색 | 파트너스 가입·API 승인 | 승인 조건·호출 제한이 낮음(착수 전 공식 문서로 재확인) | 공식이지만 범위 제한 |
| 무신사 랭킹 | 카테고리·브랜드 랭킹 | **계약 데이터 또는 운영자 가져오기** | 공개 API 없음. robots.txt가 일반 수집기를 전부 막음(`User-agent: * Disallow: /`) | 직접 수집 금지 |
| 올리브영 랭킹 | 카테고리 랭킹 | 계약 데이터 또는 운영자 가져오기 | 공개 API 없음. 자동 접근 시 403 | 직접 수집 금지 |
| 쿠팡 랭킹 페이지 | 실시간 랭킹 | 파트너스 API 범위 밖은 계약 데이터 또는 운영자 가져오기 | 자동 접근 시 403 | 직접 수집 금지 |
| 셀러 분석 도구(아이템스카우트·판다랭크 등) | 판매량 추정, 랭킹 이력 | 데이터 제휴·API 계약(유료) | 계약 조건에 따름 | 2순위. 랭킹 **이력**이 필요할 때 |
| 자사 데이터 | 주문·재고·반품·발행 관측·Meta 성과 | 이미 있음 | — | 가장 강한 신호. 학습 보정에 씀 |

**운영자 가져오기**: 운영자가 자기 계정으로 연 랭킹 화면을 CSV나 화면 저장으로 올리면, 시스템은 형식을 검사하고 스냅샷으로 남긴다. 사람이 보는 속도로만 쓰이므로 서버 부하·우회 문제가 없다. 단 약관상 허용 범위는 법무 확인을 받는다(10절 D5).

**법적 배경**: 크롤링 사건에서 형사(정보통신망법·업무방해·저작권) 무죄와 별개로, 민사에서는 데이터베이스 구축 투자를 인정해 부정경쟁행위 책임을 물은 사례가 있다(야놀자 대 여기어때). 그래서 robots.txt가 막은 곳과 약관상 금지된 곳은 자동 수집하지 않는다. 이 원칙은 출처 레지스트리에 코드로 박고, 테스트로 지킨다.

## 4. 시스템 구조

```
[수집기]  공식 API·계약 데이터·운영자 가져오기
   │  (조사 작업자 큐 product_research, 쿼터·비용 원장)
   ▼
[원본 스냅샷]  출처·수집 시각·요청 범위·본문 해시·허용 방식 (불변)
   ▼
[정규화]  키워드 묶음, 카테고리 표준표, 상품 동일성 매칭(브랜드+상품명+용량, 바코드가 있으면 우선)
   ▼
[시계열]  상품·키워드별 지표 시계열 (검색량, 추세, 조회수 속도, 순위, 가격, 판매자 수)
   ▼
[점수표]  하위 점수 9개 + 신뢰도 + 결측 표시 (결정형, 판 번호 고정)
   ▼
[MD 에이전트]  후보 발굴·비교·선정 메모 (근거 인용 필수, LLM)
   ▼
[선정 위원회 화면]  대표 승인 · 보류 · 제외 (사유 기록)
   ▼
[성장2 연결]  시장 신호 → 소싱 후보 → 카탈로그 초안 → 오퍼 → 미션 → 성과
   ▼
[학습]  출시 상품의 실제 결과로 백테스트·가중치 보정
```

### 4.1 저장(새 kind, `records` 표)

새 D1 테이블 없이 기존 규칙대로 `records`에 kind를 더하고 `lib/record-kinds.ts`에 등록한다.

| kind | 내용 |
|---|---|
| `pr_source` | 출처 레지스트리 항목: 출처 ID, 허용 방식(api·licensed·manual), 근거(약관·계약 링크), 상태 |
| `pr_snapshot` | 원본 스냅샷: 출처, 수집 시각, 요청 범위, 본문 해시, 크기, 허용 방식. 수정 불가 |
| `pr_keyword_group` | 같은 수요를 뜻하는 키워드 묶음(예: '마라 소스', '마라소스') |
| `pr_product` | 정규화 상품: 표준 이름, 브랜드, 카테고리, 가격대, 플랫폼별 외부 ID |
| `pr_series` | 지표 시계열 조각(상품·키워드 × 지표 × 기간), 각 점은 스냅샷 ID를 가리킴 |
| `pr_score` | 점수표 판: 하위 점수, 가중치 판, 신뢰도, 입력 스냅샷 해시 |
| `pr_brief` | MD 선정 메모 판: 후보, 근거 인용, 리스크, 권고(도입·관찰·제외) |
| `pr_decision` | 대표·MD 결정: 승인·보류·제외, 사유, 연결된 소싱 후보·신호 ID |
| `pr_backtest` | 백테스트 실행: 기준 시점, 관측 기간, 정밀도@k, 순위 상관, 기준선 비교 |

외부 원문 전체는 저장하지 않는다. 필요한 수치와 해시, 짧은 발췌만 남긴다. 리뷰 작성자 이름 같은 개인정보는 저장하지 않고 개수만 센다.

### 4.2 점수표(결정형)

| 하위 점수 | 주요 입력 | 메모 |
|---|---|---|
| 수요 규모 | 키워드 묶음 월간 검색수 | 로그 척도 |
| 성장 모멘텀 | 데이터랩 12주 기울기, 순위 상승 폭, YouTube 조회수 증가 속도 | 출처별 표준화 후 결합 |
| 지속성 | 계절성 분해, 반짝 유행 판별(급등 뒤 반감기) | 유행 상품은 '짧게 팔기' 표시 |
| 경쟁 강도 | 판매자 수, 상위 상품 리뷰 수, 광고 경쟁 지수, 상위 집중도 | 높을수록 감점 |
| 수익성 | 시장 가격대 − (소싱 원가·배송·채널 수수료) | 소싱 후보가 없으면 '미확인' |
| 실행 가능성 | MOQ, 납기, 재고 회전, 인증 필요 여부 | |
| 콘텐츠성 | 숏폼·리뷰 영상 반응, 시연 가능성 | |
| 브랜드 적합성 | 브랜드 아카이브 사실과의 일치 | LLM 판정, 근거 인용 |
| 리스크 | 식품표시·화장품 기능성·KC·상표·가품 신호 | 고위험은 총점과 별개로 '선정 금지' |

총점은 가중 합이지만, **결측은 0으로 채우지 않는다**. 결측이 많으면 신뢰도를 낮추고 '자료 보강 필요'로 분류한다. 이것은 앱 전체의 '미확인은 0이 아니다' 원칙과 같다. 가중치는 판 번호를 붙여 고정하고, 백테스트 결과로만 바꾼다.

### 4.3 MD 에이전트(LLM)

- 새 역할 '상품 MD'를 AI 팀에 더한다. 프롬프트는 레인 Q의 프롬프트 레지스트리에 등록 요청한다(이 계획은 Q 파일을 직접 고치지 않는다).
- 하는 일: 대표가 준 방향(예: "여름 K-스낵, 2만 원 이하")에서 키워드를 넓히고, 점수표 상위 후보를 비교하고, 선정 메모를 쓴다.
- 지키는 규칙: 메모의 모든 숫자는 스냅샷 ID를 인용한다. 인용 없는 수치, 점수표와 다른 수치는 채점기가 실패 처리한다. 모델은 점수를 **설명**할 뿐 바꾸지 않는다.
- 비용: 기존 토큰 예산(`lib/token-budget.ts`)과 사용량 원장으로 묶는다.

## 5. Collective 연결

| 연결 | 동작 | 관문 |
|---|---|---|
| 시장 신호 | 승인된 후보의 근거를 `growth_signal`로 만들고 스냅샷 계보를 붙인다. 출처가 만료되면 기존 하위 보류 전파를 그대로 쓴다 | 대표 승인 |
| 소싱 후보 | 후보 상품으로 소싱 후보 초안(단위·목표 원가·필요 인증)을 만든다. 실제 견적은 사람이 넣는다 | `mayOrder:false` 유지 |
| 카탈로그 초안 | 소싱 비교가 끝난 뒤 카탈로그 초안을 만든다 | 가격 승인은 기존 절차 |
| 기회 보드·홈 안건 | '오늘의 상품 기회'를 안건으로 올린다(내가 맡기, 1클릭 처리) | — |
| 일일 루프 | 매일 아침 수집·채점 결과를 일일 루프 기록에 붙인다 | 스위치 `product_research`(기본 꺼짐) |
| 학습 | 출시 상품의 30일 성과를 `pr_backtest`에 되돌려 가중치 보정 후보를 만든다 | 보정 적용은 승인 필요 |

절대 하지 않는 것: 자동 발주·결제, 공급자 자동 연락, 가격 자동 승인, 광고비 집행. 전역 중단이 켜지면 새 선정 연결을 막는다(수집과 채점은 계속 허용).

## 6. 화면(새 '상품 리서치' 탭)

1. **트렌드 레이더**: 카테고리·키워드 지도. 크기는 수요, 색은 모멘텀. 지난주 대비 상승 상위 20개.
2. **후보 목록**: 공용 데이터 표. 총점·신뢰도·하위 점수, 정렬·찾기·CSV.
3. **후보 상세**: 출처별 추세 그래프(같은 시간축), 경쟁 지도, 손익 시뮬레이터(원가·수수료·MOQ를 바꾸면 공헌이익이 바로 바뀜), 리스크 체크, 근거 스냅샷 목록.
4. **선정 위원회**: 후보 2~4개를 나란히 비교하고 승인·보류·제외. 사유는 한 문장으로 남는다.
5. **주간 MD 리포트**: 이번 주 신규·상승·하락·제외 후보와 지난 선정의 성적표.

UX 3차에서 만든 공용 부품, 예산 래칫, 접근성 검사를 그대로 적용한다.

## 7. 개발 단계 (PR 단위)

| 단계 | 기간 | 내용 | 완료 조건 |
|---|---|---|---|
| P0 결정·기반 | 1주 | 대표 결정(10절), 출처 레지스트리, kind 등록, 스위치 `product_research`, 루브릭·백테스트 정답셋 설계 | 레지스트리 테스트: robots·약관 금지 출처의 자동 수집 경로 0 |
| P1 공식 수집기 | 2주 | 검색광고 키워드 도구, 데이터랩 2종, 네이버 쇼핑 검색, YouTube, 쿠팡 파트너스(승인 시). 스냅샷·쿼터 원장·재시도 | 30일 수집 성공률 ≥ 98%, 쿼터 초과 0 |
| P1b 가져오기 | 1주 | 운영자 랭킹 가져오기(무신사·올리브영·쿠팡 CSV/화면 저장), 형식 검사 | 잘못된 파일 거절·부분 반영 0 |
| P2 정규화 | 2주 | 키워드 묶음, 카테고리 표준표, 상품 동일성 매칭, 시계열 | 매칭 정밀도 ≥ 95%(표본 200), 데이터랩 보정 오차 ≤ 15% |
| P3 점수표·백테스트 | 2주 | 하위 점수 9개, 신뢰도, 결측 처리, 백테스트 하네스·기준선 | ④ 4점 조건 충족, 기준선 대비 보고서 |
| P4 MD 에이전트 | 2주 | 상품 MD 역할, 선정 메모, 인용 채점기, 판사 루브릭(레인 Q 협업) | 인용 정확도 100%, 근거 없는 주장 0 |
| P5 연결·화면 | 2주 | 신호·소싱·카탈로그 초안 연결, 탭 5개 화면, 홈 안건, 일일 루프 | E2E: 승인 1회 → 소싱·카탈로그 초안, 전역 중단 시 차단 |
| P6 검증·보정 | 4~12주 관측 | 실제 운영으로 예측력 확인, 블라인드 MD 비교, 출시 상품 성과로 보정, 독립 평가 반복 | 12차원 평균 ≥ 4.7, 모든 차원 ≥ 4.5 |

PR은 단계마다 2~4개, 모두 초안 PR → CI → 병합 → 게시 → 기록 순서로 간다(UX 3차와 같은 흐름).

## 8. 4.7을 증명하는 방법

1. **백테스트**: 데이터랩은 과거 추세를 준다. 기준 시점 T에서 점수를 고정하고 T+4·8·12주의 실제 추세·순위 변화와 비교한다. 정답셋은 과거 히트 상품 50개와 비히트 대조군으로 만든다. 랭킹 이력은 계약 데이터가 있으면 바로, 없으면 P1부터 쌓은 이력으로 8~12주 뒤에 잰다.
2. **블라인드 MD 비교**: 같은 기간 같은 예산으로 에이전트 선정안과 사람 MD 선정안을 섞어, 평가자 3명이 출처를 모른 채 고른다. 에이전트 승률 ≥ 60%면 ④·⑧의 5점 근거로 쓴다.
3. **실판매 검증**: 맵달 등 실제 채널에 출시한 상품의 30일 성과를 예측과 비교한다(⑥·⑩).
4. **독립 평가**: 단계가 끝날 때마다 독립 평가자가 12차원을 채점하고, 지적을 다음 묶음에 반영한다.

## 11. 상태 어휘

이 문서의 모든 항목은 아직 계획이다. 구현·병합·게시가 일어나면 merged / published / runtime-verified, 검증은 passed / failed / blocked / not_run, 근거는 real / mocked로 따로 적는다. 실제 외부 API 호출 결과와 개발 검사(mocked)를 섞어 쓰지 않는다.
