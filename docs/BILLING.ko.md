# 선불 크레딧 요금제와 테스트 결제 (G8)

선불 크레딧은 교통카드 충전과 비슷하다. 먼저 충전(또는 매달 기본 제공)한 만큼만 AI를 쓰고, 잔액이 0이 되면 새 AI 실행이 개찰구에서 멈춘다. 이미 지나간 실행(진행 중 실행)은 되돌리지 않는다.

기술적으로는 `records`의 원장 항목(`credit_ledger`)을 합해 잔액을 계산하고, AI 제출 직전의 토큰 예산 가드(`lib/token-budget.ts` `reserve`)가 잔액 0 이하이면 확정 409로 막는다. 결제는 토스페이먼츠 **테스트 키**로만 한다.

## 스위치

| 스위치 | 기본 | 범위 | 꺼져 있을 때 |
|---|---|---|---|
| `credit_billing` | 꺼짐 | 플랫폼 스위치(운영자 워크스페이스 값만 읽음) | 원장을 만들지 않고, 가드·주문·승인·환불이 모두 동작하지 않는다(주문·승인·환불 API 409). 설정 → 사용량·비용 탭에는 요금표 미리보기만 보인다. |

- 운영자 워크스페이스: 가장 먼저 만든 관리자 계정(bootstrap)의 `workspace_owner`. 계정이 하나도 없으면(legacy) 요청 워크스페이스다(`lib/billing-server.ts` `operatorOwner`).
- 플랫폼 스위치로 둔 이유: 셀프 가입 워크스페이스의 소유자도 자기 워크스페이스의 기능 스위치를 바꿀 수 있다. 워크스페이스별로 읽으면 그 소유자가 스위치를 꺼서 정지를 피할 수 있다.
- 운영자 워크스페이스 자체는 정지하지 않는다(이메일 모드에서 계정으로 운영자가 정해진 경우). legacy에서는 요청 워크스페이스가 곧 운영자라 정지 대상이다(테스트·E2E 용도).
- 다른 워크스페이스의 기능표에도 스위치가 보이지만 바꿔도 효과가 없다. 화면에서 숨기는 일은 기능 스위치 라우트 담당 레인의 후속이다.

## 요금제(자리 표시)

가격은 모두 **가격 미정 — 대표 확정 필요**다. 화면도 같은 문구를 붙인다. 상수는 `lib/billing.ts`.

| 요금제 | 월 기본 제공 | 월 가격(공급가) | 상태 |
|---|---|---|---|
| Free | 200크레딧(약 20만 토큰) | 0원 | 확정 |
| Starter | 2,000크레딧 | 49,000원 | 가격 미정 — 대표 확정 필요 |
| Growth | 10,000크레딧 | 199,000원 | 가격 미정 — 대표 확정 필요 |

이 판에서 모든 워크스페이스는 Free다. 유료 요금제 전환(정기결제)은 가격 확정과 자동결제 별도 동의 화면이 생긴 뒤 연다. 충전 상품(자리 표시): 크레딧 1,000 = 공급가 10,000원, 크레딧 5,000 = 공급가 45,000원. 화면과 결제 금액은 늘 부가세 10%를 더한 총액이다(1,000크레딧 = 11,000원).

## 크레딧 환산과 원장

- 1크레딧 = 1,000토큰. 한국 시간 달력 월마다 그 달 보고 토큰 합계(모든 공급자, `provider_usage`의 `totalTokens`, 없으면 입력+출력)를 1,000으로 나눠 올림한다. 토큰을 모르는 실행은 세지 않는다(토큰 예산과 같은 규칙).
- 과금 시작 시각(`billing_account` 1행)은 스위치가 켜진 뒤 처음 원장을 읽을 때 정하고 바꾸지 않는다. 그 전의 사용은 빼지 않는다.
- 원장 항목: `grant`(월 기본 제공, +) · `purchase`(충전, +) · `usage`(AI 사용, -) · `refund`(환불, -) · `expiry`(기본 제공분 월말 소멸, -). 잔액 = 항목 합계.
- 소멸: 그 달 사용은 그 달 기본 제공분에서 먼저 빠지고 남은 기본 제공분만 월말에 소멸한다. 충전 크레딧은 이 판에서 소멸하지 않는다(유효기간 정책은 대표 확정 필요).
- 월별 항목(grant·usage·expiry)은 같은 id(`grant-YYYY-MM` 등)로 다시 계산해 덮어쓴다(멱등). 기본 제공량은 처음 기록한 값을 유지한다.
- 동기화 시점: 요약 화면 GET, AI 제출 직전 가드, 환불 요청. 스위치가 꺼져 있으면 동기화하지 않는다.
- 소프트 캡: 가드는 잔액 0 이하일 때만 막는다. 잔액이 조금 남은 상태에서 시작한 큰 실행은 끝난 뒤 잔액을 음수로 만들 수 있다(토큰 예산 가드와 같은 한계).

## 사용량 알림

이번 달 쓸 수 있던 크레딧(이번 달 사용 + 현재 잔액) 중 80%·100% 이상을 쓰면 `billing_alert`(월·단계당 1행)를 남긴다. 설정 → 사용량·비용의 '요금제와 크레딧' 카드에 보인다.

**남은 일:** 홈 '오늘의 안건'은 캠페인 범위 항목만 그린다(`lib/agenda-server.ts`). 워크스페이스 범위 알림 출처를 추가하는 일은 안건 담당 레인에 넘긴다. 이 PR은 알림 기록까지만 한다.

## 결제(테스트 모드)

흐름은 토스 결제창(V2 SDK `https://js.tosspayments.com/v2/standard`) 리다이렉트 방식이다. 앱 화면에는 CSP가 없어 스크립트를 막지 않는다. 스크립트는 '요금제와 크레딧' 카드에서 구매를 누를 때만 불러온다.

1. `POST /api/billing/checkout {packId}`(소유자): 서버 상수로 부가세 포함 총액을 계산해 `billing_order`(상태 `pending`)를 만든다. orderId는 `col_` + UUID(32자, 토스 규칙 6~64자·영숫자·`-`·`_`).
2. 화면이 `TOSS_PAYMENTS_CLIENT_KEY`(시크릿 키와 같은 모드일 때만 응답에 실림)로 결제창을 연다. 클라이언트 키가 없으면 결제창을 열지 않고 멈춘다(청구 없음).
3. 결제창이 `/?view=settings&section=usage&billing=success&paymentKey&orderId&amount`로 돌려보내면 화면이 `POST /api/billing/confirm`을 부른다.
4. 서버: 금액이 저장된 주문 금액과 다르면 토스를 부르지 않고 400. 같으면 주문을 `confirming`으로 선점(동시 요청 중 하나만)하고 `POST https://api.tosspayments.com/v1/payments/confirm {paymentKey,orderId,amount}`를 `Authorization: Basic base64(시크릿키 + ':')`, `Idempotency-Key: confirm-<orderId>`로 보낸다.
5. 응답 `status=DONE`·같은 orderId·`totalAmount`=주문 금액이면 같은 batch에서 주문 `paid`와 `purchase-<orderId>` 원장 항목을 남긴다. 4xx(429 제외)는 `failed`, 429·5xx·연결 오류는 `unknown`(같은 버튼으로 다시 확인, 같은 멱등 키라 중복 승인 없음).
6. 이미 같은 paymentKey로 승인된 주문을 다시 확인하면 토스를 부르지 않고 같은 결과를 준다. 다른 paymentKey는 409.

키 규칙(`lib/billing.ts` `checkSecretKey`):

- `TOSS_PAYMENTS_SECRET_KEY`가 없으면 503(주문도 만들지 않음).
- `test_`로 시작하지 않으면 `BILLING_LIVE=1`이 없는 한 503. **실결제 전환(`BILLING_LIVE=1`, 라이브 키 등록)은 대표의 결정이다.** 에이전트는 라이브 키를 넣거나 이 값을 켜지 않는다.
- 키는 Sites/Workers 비밀값으로만 넣는다. 소스·문서·채팅에 원문을 적지 않는다.

환불(`POST /api/billing/refund {orderId}`, 소유자): 구매 버튼과 같은 모양의 '환불 요청' 한 번으로 요청한다. 구매만큼 크레딧이 남아 있으면 `POST /v1/payments/{paymentKey}/cancel {cancelReason}`(멱등 키 `refund-<orderId>`)로 취소하고 `refund-<orderId>` 항목을 남긴다. 일부를 이미 썼으면 막지 않고 `refund_requested`(담당자 확인)로 접수한다. 부분 환불 계산은 환불 정책 확정 뒤 구현한다.

가정(공식 문서를 직접 열지 못해 검색 요약으로 확인한 것, 실연동 전 다시 확인): V2 SDK 호출 `TossPayments(clientKey).payment({customerKey}).requestPayment({method:'CARD',amount:{currency:'KRW',value},orderId,orderName,successUrl,failUrl})`, `customerKey`는 `TossPayments.ANONYMOUS`, 취소 API 경로와 본문, 승인 10분 만료, `Idempotency-Key` 헤더 지원.

## 테스트 모드 절차

1. 토스페이먼츠 개발자센터에서 테스트 키(클라이언트 `test_ck_…`, 시크릿 `test_sk_…`)를 받는다(대표 계정).
2. 운영자 소유자가 비밀값 `TOSS_PAYMENTS_SECRET_KEY`, 환경값 `TOSS_PAYMENTS_CLIENT_KEY`를 넣고 기능표에서 `credit_billing`을 켠다.
3. 설정 → 사용량·비용 → '요금제와 크레딧'에서 충전 상품을 고른다. 테스트 결제창에서 테스트 카드로 결제하면 실제 청구는 없다.
4. 돌아온 화면에서 '결제를 확인했습니다'와 잔액 증가, 결제 내역 '결제 완료'를 확인한다. '환불 요청'으로 취소를 확인한다.
5. 스위치를 끄면 원장·가드·결제가 멈춘다(기록은 남는다).
