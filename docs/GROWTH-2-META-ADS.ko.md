- 위치: 성장2 **E-M(온라인 채널 확장의 Meta 광고 트랙)**. C 시장 레이더, D 실험, F 실행 권한, G 증분 측정, H 고객 자산, I 개선 루프를 연결한다. 별도의 독립 광고 관리 앱을 만들지 않는다.

## 1. 목표와 사용자 경험

**브랜드를 이해하는 AI 팀이 무엇을 누구에게 어떤 콘텐츠·오퍼로 팔지 제안하고, 승인된 광고 실험을 운영하며, 실제 구매와 남는 이익으로 다음 실행을 개선한다.**

Meta는 광고 전달·경매·플랫폼 최적화를 맡는다. COLLECTIVE는 브랜드 사실, 상품·재고·마진, 콘텐츠 가설, 실험 설계, 실행 승인, 주문 대조와 개선 지식을 맡는다. 플랫폼 최적화 기능을 사용할 때는 그 설정과 변경 이력을 실험 조건으로 기록한다.

대표의 기본 흐름은 **판매 목표 입력 → 실행안 묶음 검토 → 승인 범위 지정 → 예외 확인 → 주간 계속/중단/개선 판단**이다. 매 광고의 자잘한 수정을 계속 요구하지 않도록 같은 승인 범위의 반복 작업을 묶고, 소재·예산·기간·상품 조건이 범위를 벗어날 때만 다시 요청한다.

| 경로 | 고객 흐름 | 주요 목표 | 성공으로 세지 않는 것 |
|---|---|---|---|
| 자사몰 구매 전환형 | 광고 → 상품/기획전 랜딩 → 결제 → 취소·환불 반영 | 실제 결제 주문, 신규 고객 획득비, 광고 후 기여이익 | 광고 클릭, 결제 페이지 방문, 테스트 주문 |
| 콘텐츠 기반 전환형 | 릴스·영상·이미지·기존 게시물 → 브랜드/상품 콘텐츠 → 자사몰 또는 검증 가능한 예약·문의 → 구매 | 콘텐츠별 구매·이익 기여. 문의는 별도 중간 단계 | 조회수·좋아요·팔로워만으로 매출 성공 판정 |

콘텐츠 자체의 인지도·참여 목표도 선택할 수 있지만 해당 캠페인은 매출 미검증으로 표시한다. 자사몰이 없으면 콘텐츠·오퍼 설계와 읽기 분석부터 가능하며, 결제나 후속 전환을 관측할 수 없는 상태에서 구매 최적화가 준비됐다고 표시하지 않는다. 두 경로를 동시에 열기보다 한 브랜드·한 상품군·한 전환 경로를 첫 파일럿으로 선택한다.

| 전략·실험 설계 | 고객 문제→오퍼→훅→증거→CTA 가설, 대조군·최소 표본·종료 기준, 확인할 가정 제안 | 8개 역할·팀 회의·D 사전등록 실험 |

| 광고 준비·집행 | 캠페인/광고세트/광고 매핑, 먼저 비활성 초안 생성, 승인 후 켜기·정지·제한된 변경, 외부 상태 재조회 | 성장1 발행/실험 연결. Buffer 유기 게시와 Meta 유료 광고는 공급자별로 분리 |
| 전환 측정 | 자사몰 주문 어댑터, UTM·광고 ID·소재 버전 연결, Pixel/CAPI 이벤트 계약·중복 제거·재시도 | 주문 원장·비용·귀속. 첫 자사몰 스택 1종, 후속 어댑터 확장 |
| 분석·개선 | 소재/오퍼/랜딩별 퍼널, 추적 이상·피로 의심, 계속·중단·추가 실험 제안, 규칙 초안 | 품질 콘솔·플레이북·개선 루프 대장·A8 보고서 |

유기 게시물의 반응이 좋으면 유료 실험 후보로 올릴 수 있다. 그것만으로 광고 승자·인과 효과라고 판정하지 않는다. 이미지·영상 생성 외부 서비스 연결은 별도 어댑터와 사용 권한을 검증하며 MVP는 검수한 실제 파일로도 실행 가능하게 한다.

## 3. 측정과 학습 계약

- 연결 계보: 브랜드 → 캠페인/판매 미션 → 가설·실험 안 → 상품·오퍼·랜딩·소재 버전 → Meta 객체 ID → 성과 스냅샷 → 주문 대조 → 판정 → 플레이북 후보. 기존 ID를 참조하고 주문·실험 원장을 중복 생성하지 않는다.
- Meta 보고 수치, 자사몰 실제 순매출, COLLECTIVE 귀속 수치, 통계적으로 검증한 증분은 별도 열로 저장·표시한다. 주문이 있다는 이유만으로 광고 귀속을 확정하지 않는다.
- 주문 원장이 결제·취소·환불의 정본이다. 통화·시간대·부가세 기준·귀속 기간·집계 시각·성숙 대기 기간을 저장한다. 부분 환불·지연 전환은 원장의 해당 기간을 정정하고 기존 보고서 버전과 차이를 남긴다. Meta에 보낼 정정 이벤트는 지원 방식 확인 후 구현하며 임의의 음수 Purchase를 보내지 않는다.
- Pixel과 CAPI에 같은 사건을 보내면 안정적인 event_id와 같은 event_name을 사용한다. 주문 ID 기반 중복 방지와 광고 이벤트 중복 방지는 각각 검증한다. 웹훅 반복·역순·재시작에서도 한 결제가 두 매출이 되지 않아야 한다. 테스트 이벤트·주문은 운영 성과에서 제외한다. [M1]
- 동의·전송 목적·허용 필드·보존·삭제 기준을 먼저 정한다. 동의 조건이 충족되지 않으면 전송을 차단하고 측정 공백을 표시한다. 고객 식별 원문·광고 자격증명은 LLM 입력과 로그에 넣지 않는다. 해시 처리만으로 익명화가 끝났다고 보지 않는다. 리타기팅/고객 목록은 적법한 사용 조건을 별도로 확인한다.
- 광고 후 기여이익 = 동일 회계 기준의 환불 차감 매출 − 상품 원가 − 변동 배송/포장/결제 비용 − 광고비 − 해당 제작·모델 비용. 원가 누락은 미확인으로 표시한다. 신규 고객 CAC와 전체 주문 CPA를 분리한다. 이 값도 귀속 기반이면 인과적 증분 이익으로 이름 붙이지 않는다.
- 학습 판정은 관찰 가설 → 실험 후보 → 사전등록 검증 → 채택/보류/기각으로 관리한다. 계절성·오퍼·타깃·게재 위치·자동 소재 변형이 동시에 바뀌면 효과를 분리할 수 없다고 표시한다. 탐색용 밴딧과 확증용 홀드아웃의 결과를 섞지 않는다.
- 표본 부족·전환 지연·추적 누락을 실패나 개선으로 단정하지 않는다. 신규 채널의 첫 제한 실험에는 기존 매출을 요구하지 않지만, 자동 확대에는 사전 정의한 증거와 유효한 위임이 필요하다. 프롬프트 개선 평가는 기존 봉인 세트를 보호한다.

## 4. 집행 제어와 운영 루프

| 행동 | 계획상 기본 권한 | 재확인 조건 |
|---|---|---|
| 연결된 계정의 읽기·분석 | 허용 계정에서 T0 | 권한·자산 소유 관계 변경 |
| 로컬 광고 초안·소재 실험안 | T1 | 외부 광고 객체 생성은 연결/쓰기 범위 확인 후 |
| Meta 비활성 객체 생성 | 별도 쓰기 플래그, PAUSED 확인 | 계정·브랜드·랜딩 불일치 또는 심사 실패 [M2] |
| 최초 활성화·비용 발생 | 승인한 계정·상품·소재·기간·예산 범위에서 T3 | 최초 집행은 사람 승인. 성과 점수만으로 지출 권한을 얻지 않음 |
| 이후 반복 집행·예산 조정 | 검증 후 사전 위임 범위에서만 | 총액·기간·허용 소재군·변경폭 밖이면 재승인 |
| 중단 | 승인된 운영 범위에 긴급 정지 포함 | 정지 요청 성공과 외부 실제 정지 확인을 구분 |

새 기능 플래그는 읽기, 외부 초안 쓰기, 활성화/예산 변경, 전환 이벤트 전송을 분리해 기본 꺼짐으로 설계한다. 계정·브랜드 교차 사용, 만료 승인, 내용 변경 후 이전 승인 재사용을 거부한다.

예산은 총액·일별 운영 목표·기간·손실 한도·안전 여유를 함께 관리한다. **앱의 폴링이나 일일 예산만으로 실제 청구액의 절대 상한을 보장하지 않는다.** 적용 가능한 공급자 한도·종료 시각과 앱 예약 장부를 병행하고, 통계 지연·정지 지연을 여유분에 반영한다. 상한/중단 기준 미설정이면 활성화하지 않는다. 안전 여유와 실행 금액은 첫 파일럿 승인 때 정한다.

API 타임아웃 후 같은 광고를 무작정 다시 만들지 않는다. 요청 키·외부 ID·실행 잠금과 재조회로 결과를 확정하고, 결과불명 상태에서는 새 지출을 막는다. 광고 관리자에서 사람이 바꾼 값도 감지해 로컬 승인과 대조한다. 심사 거절·계정 제한을 다른 계정이나 브라우저 자동화로 우회하지 않는다.

| 점검 주기(초기 제안) | 행동 조건 | 자기 검증 | 보존 상태 | 중단 | 출력 |
|---|---|---|---|---|---|
| 집행 중 15분, 계정 한도에 맞춰 조정 | 활성 광고/미확정 요청 존재 | 권한·승인 범위·공급자 상태·지출 신선도 대조 | 마지막 성공 시각·외부 ID·예약 예산 | 추적/권한 오류, 한도 여유 부족이면 확대 차단·사전 승인한 정지 요청 | 예외 카드, 정지 확인 여부 |
| 일 1회 + 주문 웹훅 | 새 성과·주문 또는 지연 정정 | 중복·환불·통화·귀속 기간 대조 | 데이터 기준 시각·정정 버전 | 데이터 불일치면 판정 보류 | 퍼널·CPA·CAC·기여이익 |
| 사전등록 종료 시점 | 기간·표본 또는 조기 중단 조건 도달 | 배정·표본·전환 성숙·동시 변경 검사 | 실험 판정·근거 | 불충분이면 채택·확대 금지 | 계속/중단/재실험 카드 |
| 주 1회 | 종료된 실험과 승인된 교정 | 브랜드별 일반화 가능성·기존 규칙 회귀 점검 | 규칙 버전·적용 범위·되돌릴 버전 | 반증/회귀 시 보류·롤백 | 다음 주 실험안, 대표 결정 묶음 |

모든 루프는 서버 작업자가 이어받고 재시작·중복 실행·조회 실패·정지 실패를 기록한다. 대표에게 매번 같은 알림을 보내지 않도록 원인별 묶음과 해제 조건을 둔다. 기간이 지났다는 이유만으로 예산을 자동 확대하지 않는다.

| 카드 | 구현 범위 | 완료를 판정할 증거 | 의존성 |

## 6. 성장2 로드맵에 넣는 위치

- **첫 2주 제안:** M0, M1/M2의 계약·격리 검증, M3의 소재/실험 작업대. 자사몰 스택과 권한 확인이 선행된다. 연결이 늦으면 수동 통계·주문 가져오기 및 로컬 초안까지 진행하고 지출은 시작하지 않는다. 담당 확정 후 공수를 다시 산정한다.
- **1단계(원안 1~8주):** 한 브랜드·한 상품군·한 전환 경로에서 M1~M5 최소 연결. 명시 승인된 한도 내 첫 제한 실험. 자사몰 구매와 콘텐츠 경로를 모두 개발 완료해야 첫 실험을 시작하는 조건은 두지 않는다.
- **2단계(원안 9~16주):** M6와 검증된 경로의 반복 운영. 허용 범위 내 소재 교체·중단, 증거가 충분한 경우 승인된 예산 조정. 대상/상품 확대는 별도 결정.
- **3단계:** 카탈로그 광고·다브랜드·고객 사용권을 갖춘 리타기팅, 영상 렌더러, 다고객 연결은 성과·데이터·권한을 확인한 뒤 확장한다. 첫 MVP 필수 범위에 모두 넣지 않는다.

기존 G0의 3주 주문·귀속률·누적 라벨 조건은 첫 판매를 막는 입구로 쓰지 않는다. 성장1 개발 종료 뒤 M0~M4 개발/검증을 시작할 수 있고, M5는 결제/전환 경로·재고/배송·권한·예산/손실/기간이 준비돼야 한다. 대규모 자동 확대와 자기개선은 각 기능의 평가·표본·증분 근거가 필요하다. 이는 성장1 공통 종료 기준 7절의 적용이며 안전·평가 조건을 면제하지 않는다.

## 8. 기술 근거와 재확인 범위

- [M1] Meta 공식 Conversions API 문서: 브라우저/서버 이벤트 병행, event_id·event_name 중복 제거, 이벤트 공유 동의 전제. [공식 문서](https://developers.facebook.com/docs/marketing-api/conversions-api/set-up-conversions-api-as-a-platform?locale=fr_FR). 2026-09-28 열람. 이 문서의 플랫폼 서비스 심사 요건을 모든 자사 계정 연결에 그대로 적용하지 않고 실제 사용 형태별로 재확인한다.
- [M2] Meta 공식 Python Business SDK Ad 객체: PAUSED/ACTIVE, configured_status/effective_status, pending_review/disapproved 및 validate_only 모델. [공식 소스](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/ad.py). 2026-09-28 열람. PAUSED는 이 계획의 기본값이며 API 전체의 자동 기본값이라고 주장하지 않는다.
- 광고·성과 API 버전, 승인 권한, 자동 최적화 옵션, 게재 위치, 예산 제한, 이벤트 필드는 구현 시점의 공식 문서와 실제 계정에서 확정한다. 공식 개발자 문서 일부는 이번 조회에서 429여서 세부 최신값을 확정하지 않았다.
- 기능 범위·주기·카드·지표·예산 제어는 COLLECTIVE의 설계 제안이다. Meta가 이를 모두 자동 보장한다는 뜻이 아니다. 이번 추가에서 성장2 원안의 시장·규제 주장 전체를 재검증하지는 않았다.
