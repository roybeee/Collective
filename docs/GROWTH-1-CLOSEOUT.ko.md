## 1. 공통 결론과 범위 고정

**현재 승인된 필수 코드와 연결을 마무리하고, 통합 검사·운영 배포 확인·잔여 인계를 끝내면 성장1 개발을 종료한다. 실제 주문·사람 라벨·관측 기간이 필요한 항목은 운영 인수와 효과 검증으로 계속 관리한다.**

1. 새 판매 플랫폼·자율 광고 집행·상품 MD·새로운 판매 미션 엔진을 성장1 종료 조건에 더하지 않는다. 성장2 범위다.
2. 기존 수용조건을 깨는 결함, 병합 과정의 기능 유실, 권한/비용/데이터 정합성 결함은 성장1에서 고친다. “성장2에서 수정”으로 넘겨 개발 종료를 선언하지 않는다.
3. 기존에 제외한 Android·전체 포맷 변경·스키마 전면 개편을 다시 열지 않는다. 트랙 R의 전체 종료도 성장1 종료 조건이 아니다. 다만 공유 변경으로 생긴 회귀는 해당 소유 레인이 해결한다.
4. 아래 필수 목록의 기능은 대체 PR로 구현할 수 있다. 특정 PR을 병합했다는 사실만으로 수용조건을 통과한 것은 아니다.
5. 새로운 요구는 별도 후속 목록에 넣는다. 필수 종료 범위를 추가·삭제하려면 대표 결정 또는 유효한 기존 위임과 이유를 명시한다. 각 세션이 독자적으로 결승선을 옮기지 않는다.

- B5처럼 과거 병합 뒤 사라진 기능은 복원/동등 대체와 검사 근거 없이는 C08을 통과할 수 없다. 최신 main 통합에서 의도하지 않은 삭제를 포함한 PR을 그대로 게시하지 않는다.

## 4. 개발 종료의 공통 검사·배포 조건

아래 전부가 충족돼야 `개발 종료 passed`다.

1. **범위:** C01~C12가 기능별 근거로 처리됐다. 필수 코드 미구현·통합 충돌·권한/데이터/예산 결함은 남지 않았다. 조건부 실행만 5절로 인계할 수 있다.
2. **소스:** 해당 PR이 `merged`이고, 최종 통합 커밋에서 필요한 코드·라우트·테스트가 존재한다. PR 작성 당시 통과와 통합 후 통과를 구분한다.
3. **기존 필수 검사:** 아래 명령을 최종 통합 소스 또는 그와 동일한 제품 소스의 CI에서 확인한다. 기존 `.github/workflows/ci.yml`의 차단 조건을 낮추지 않는다. `e2e-smoke`는 현재 CI에서 비차단이므로 workflow success만으로 E2E 성공을 주장하지 않고 개별 결과·해당 변경의 실제 여정을 적는다.

   ```sh
   node scripts/test.mjs
   node node_modules/typescript/bin/tsc --noEmit
   node scripts/lint-gate.mjs
   node scripts/check-prompts.mjs
   node scripts/run-framework.mjs build
   python3 tests/research_worker_test.py
   python3 tests/research_install_test.py
   ```

4. **변경 경로:** 성과 수집·발행 연결·Reflector·digest·입력 축소·회전·리플레이의 해당 검사와 화면/라우트 근거를 연결한다. 외부 서비스 stub·로컬 D1·실브라우저·운영 실계정을 구분한다. 기존 passed 증거를 의미 없이 반복 실행하지 않는다.
5. **배포:** A가 최종 제품 묶음을 `published`하고 [PUBLISH](PUBLISH.ko.md)의 `runtime-verified` 정의로 확인한다. `/api/version/public`만의 tree 일치로 소유자 API·기능 상태까지 확인했다고 쓰지 않는다. 최신 main에 미게시 제품 변경이 있으면 그대로 표시한다. 프롬프트만 바뀐 것은 별도 `registry-active` 근거를 쓴다.
6. **운영 기본 상태:** 소유자 로그인·기존 역할/회의 진입·연결 상태·새 화면/API의 권한/꺼짐·작업자 연결·주문/보고 조회 경로를 확인한다. 실제 활성 기능에서 발생하는 결함을 “스위치 꺼짐으로 인계”해 감추지 않는다. 외부 데이터/자격이 없어 못 켠 새 기능은 5절에만 적는다.
7. **복구·인계:** 새 스위치의 기본값/현재값·실제로 검증한 범위·되돌릴 버전·담당·남은 활성화 조건을 남긴다. 키 회전처럼 스위치만 끄면 돌아오지 않는 변경은 별도 복구 조건을 명시한다. 게시 뒤 24~72시간 감시는 Q가 인수하고, 기준선·기간·중단조건을 PUBLISH 기준으로 기록한다. 감시 종료 전에는 운영 인수의 감시 항목을 passed로 처리하지 않는다.
8. **기록:** 8절 서식의 종료 판정 기록을 A가 모은다. G는 자기 코드 근거, Q는 평가/운영 감시, A는 통합·게시·인수를 확인한다. 새 일괄 게시 권한이나 타 레인 PR 대리 병합 권한을 부여하는 절차가 아니다.

## 5. 개발을 무기한 열어 두지 않는 조건부 인계

`blocked/not_run`은 삭제나 성공이 아니다. 각 항목에는 **원인, 이미 된 코드/검사, 담당, 재개 조건, 다음 확인일(KST), 실행 한도/권한, 영향받는 기능, 후속 기록 위치**가 있어야 한다. 담당과 다음 확인일이 없는 “나중에”는 인계 미완료다.

코드나 통합 검사 실패를 표본 부족으로 바꾸지 않는다. 법률·공급자·예산 조건을 문서만으로 충족했다고 선언하지 않는다. 기한이 지나면 담당자가 `blocked` 원인과 재개/범위 조정안을 갱신한다. 새 조사나 평가를 무제한 반복해 같은 문턱을 넘기려 하지 않는다.

## 6. 운영 인수의 최소 실사용 경로

한 브랜드·한 판매/측정 경로에서 아래를 확인한다. 이미 충족한 real 기록은 해당 코드 변경 영향을 검토해 재사용한다. 실행 권한이 없는 실제 게시·지출·고객 발송을 종료 증거를 만들려고 실행하지 않는다.

| 항목 | real 증거 | 부족할 때 |
|---|---|---|
| 산출물·교정·자료 요청 | 실제 역할 실행의 사용량/버전 연결, 사유 있는 반려→재작성, 승인 규칙 주입, 자료 요청→사실 확정으로 닫힘 | 해당 단계만 blocked와 담당/다음 확인일 |
| 게시·성과 수집 | 허용된 실제 게시의 공급자 결과, 코드/실험 안/게시물 ID, 실제 수집값·기간·출처와 실패 복구 상태. 직접 연결을 쓰지 않는 경로는 수동 여부 표시 | Buffer 접수만으로 published 주장 금지. 첫 실게시 미실행은 결정16 `not_run`·L2 축소 유지 |
| 주문·비용 | 실제 고객 주문 1건 이상을 가져오거나 기록, 추적 근거·비용·취소/환불 처리와 중복 방지 확인, 해당 기간 POS/원장 합계 대조 | 샘플 CSV/테스트 주문으로 실매출 성공 처리 금지. 데이터 0이면 L3/L4 미확인/보류 유지 |
| 보고서 | 끝난 주의 실제 주문과 POS 합계로 A8 미리보기→동결→대표 검토 1건. 장부와 숫자 일치 | 진행 중인 주를 종료 주처럼 만들지 않음. 입력 없으면 A8 real 종료 not_run |
| 품질·비용·복구 | 켠 기능의 해당 평가/실행 근거·설정된 비용 한도·경보/중단 경로, 게시 뒤 기존 24~72시간 감시 결과 | 표본 부족은 insufficient. 장애가 있으면 영향 경로 수정/중단, 성공으로 표시 금지 |

환불/재시도 등 실제로 발생하지 않은 실패 상황은 적절한 격리 테스트 증거를 함께 쓴다. 고객에게 불필요한 주문 취소·발송을 만들어내지 않는다. 실계정 성공과 실패 케이스 검증의 real/mocked 범위를 분리한다.

## 7. 성장계획2로 넘어가는 기준

## 8. 모든 세션의 작업·보고 규칙

1. 작업 시작/재개 때 최신 main의 `AGENTS.md` → `LANES.ko.md` → 본 문서 → STATUS 자기 레인을 읽는다. 이미 진행 중인 세션도 다음 PR/병합 전 대조한다.
2. 다음 작업은 C01~C12 중 자기 레인 미완료 항목에서 고른다. 기존 PR·파일 소유를 확인하고, 겹치면 기존 작업에 연결한다. #213→#219 순서는 지킨다. 공유 파일은 LANES대로 통합한다.
3. 상태는 STATUS 자기 칸에 적는다. 공용 운영 표·게시 대기열 처리·릴리스 기록은 A가 관리한다. 본 기준 문서에 매번 PR 상태를 복제하지 않는다.
4. 종료 인계의 기능별 행은 아래 형식을 사용한다. C 항목에 기능이 여러 개면 하위 행으로 나누고, 일부 실패를 묶어서 passed로 만들지 않는다.

   | C-ID/기능 | 담당 | PR·최종 소스 SHA | 검사 결과·증거(real/mocked) | published/runtime-verified/registry-active 근거 | 현재 스위치·사용 범위 | blocked/not_run·이유·다음 확인일 | 후속 소유자/재개 조건 |
   |---|---|---|---|---|---|---|---|
   | 작성할 항목 | A/G/Q/기존 소유자 | 실제 값 | 실제 실행 결과 | 해당하는 것만 | 기본값과 운영값 구분 | 해당하는 것만 | 빠짐없이 |

5. A는 `docs/observations/<날짜>-lane-a-growth1-closeout.md`에 최종 판정을 모은다. G/Q는 자기 관찰 기록 링크를 제공한다. 기록에 다음을 포함한다.
   - 판정 시각(KST/UTC), 최종 main SHA, 게시 제품 SHA/tree, 운영 응답, 레지스트리 별도 상태.
   - `개발 종료 / 운영 인수 / 효과 검증` 각각의 passed/failed/blocked/not_run과 사유.
   - C01~C12 처리 근거와 미해결 필수 결함 수. **필수 결함이 남으면 개발 종료 passed 불가**.
   - 조건부 인계 전체 목록, 담당·다음 확인일·재개 조건, 감시 기간과 담당.
   - 성장2가 재사용할 기능과 아직 사용할 수 없는 기능, 첫 허용 작업.
6. 개발 종료 뒤 신규 기능은 성장2/후속 계획으로 받는다. 성장1 결함이 실제 발견되면 해당 항목만 다시 열고 원인·영향·수정/배포 근거를 남긴다. 프로젝트 전체를 근거 없이 처음부터 재시작하지 않는다.
