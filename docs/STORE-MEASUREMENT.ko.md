# 점포 실측 (A4-1·A4-2)

- 범위: [성장 계획](GROWTH-PLAN.ko.md) 에픽 A4의 1·2차분이다. A4-1은 점포 장부 쪽 귀속 집계, A4-2는 게시(publication) 단위 귀속이다(`exec-loop-4` 권고 (1)(2)(3)(5)의 점포 쪽). PNG에 코드를 넣는 일, 수동 주문 입력의 코드 조회, 수동·소재 단위 귀속의 게시 검증은 A4-3, 캠페인 성과 탭 자동 집계는 PR 4b로 넘겼다([범위 밖](#범위-밖)).
- 정본: 판정·저장·권한은 `lib/store-operations-server.ts`(`measurementAction`)가 정한다. 게시별 코드 발급은 `lib/publication-codes.ts`다. 순수 규칙은 `lib/tracking-codes.ts`(코드), `lib/order-import.ts`(CSV), `lib/store-attribution.ts`(귀속·게시 관문·집계·완전성·incrementality-lite)에 있다. 화면 표시 판정은 `lib/store-operations-view.ts`에 있다.
- 화면: 점포 마케팅 → 지점 → **주문 장부** 탭 안에 **주문·비용**, **추적 코드**, **주문 가져오기**(관리자만), **귀속 보고** 탭이 있다.

## 결론

추적 코드로 주문을 캠페인에 잇는다. 주 단위로 POS 합계와 맞춰 본 주만 성과로 센다. 이렇게 센 숫자도 광고의 순증 효과는 아니다.

## 비유

계산대 옆 쿠폰함과 같다. 손님이 낸 쿠폰(추적 코드)을 모아 두면 어느 전단을 보고 왔는지 알 수 있다. 다만 전단이 없었어도 올 손님이 쿠폰을 냈을 수 있다. 그리고 그날 금고 정산(POS 합계)과 쿠폰함 장부가 맞지 않으면 그날 기록은 믿지 않는다.

## 흐름과 권한

| 단계 | 작업(`/api/store-operations` POST `action`) | 권한 |
|---|---|---|
| 코드 목록·스위치 상태 조회 | `list` | 로그인한 모든 역할 |
| 추적 코드 만들기 | `create_tracking_code` | 관리자(소유자 포함) |
| POS CSV 미리보기 | `import_orders`(`csv`, `dryRun` 기본값 true) | 로그인한 모든 역할. 화면은 관리자에게만 탭을 보인다. |
| POS CSV 확정 | `import_orders`(`csv`, `dryRun:false`) | 관리자 |
| 장부 양식 CSV 가져오기 | `import_orders`(`rows`) | 로그인한 모든 역할(주문 기록 저장과 같은 권한, 기존과 같음) |
| POS 주간 합계 입력 | `set_pos_total` | 관리자 |
| 귀속 보고 | `attribution_report` | 로그인한 모든 역할 |

- 게시별 코드 발급은 이 API의 작업이 아니다. 실행 쪽 발행 초안 저장이 관리자를 확인한 뒤 `issuePublicationCode`를 부른다([게시별 코드 발급](#게시별-코드-발급)).
- 목록·귀속 보고·POS CSV 미리보기는 저장하지 않으므로 워크스페이스 쓰기 잠금을 잡지 않는다. 다른 화면이 저장하는 중에도 열리고, 보관한 지점도 목록과 귀속 보고는 볼 수 있다.
- **주문·비용** 탭의 **장부 양식 CSV**(빈 양식 받기 포함)는 기존 장부 양식 가져오기 그대로다. 원가·환불액·상태·실험·캠페인/소재 귀속 열을 한 번에 넣을 때 쓴다. 이 경로도 주문번호의 휴대폰 번호, 출처 메모·유입 확인 근거의 휴대폰·카드번호 패턴을 거부한다.
- 관리자에게 보이는 **POS CSV 가져오기** 버튼은 **주문 가져오기** 탭(열 매핑·미리보기)으로 연결된다.

## 자동 귀속 스위치 `a4_auto_attribution`

- 기본은 꺼짐이다. 워크스페이스 소유자만 켜고 끈다(`POST /api/feature-flags` `{action:'set', flag:'a4_auto_attribution', enabled}`, 기본값 복귀는 `{action:'reset'}`). 게시 없이 다음 요청부터 반영된다.
- 꺼짐: 추적 코드가 맞는 주문도 캠페인 없이(미귀속) 저장한다. 주문에는 읽은 코드만 남는다. 귀속은 주문 기록 창에서 사람이 캠페인·소재·확인 근거를 고르는 수동 귀속뿐이다. 화면은 '자동 귀속 꺼짐 — 소유자가 기능 스위치에서 켤 수 있음'을 보인다.
- 켜짐: 가져오는 주문의 코드가 이 지점 코드와 맞고, 적용 시작일 이후 주문이며, 코드의 캠페인이 아직 유효하면 그 캠페인·소재·유입 채널·팔로 귀속한다. 게시에 묶인 코드는 [게시 관문](#게시-관문)도 통과해야 한다. 코드가 여럿이면 첫 유효 코드로 귀속하고 나머지는 충돌로 기록한다. 등록되지 않은 코드와 캠페인·게시가 삭제된 코드는 귀속하지 않는다.
- 스위치는 가져오는 순간에만 적용한다. 이미 저장한 주문을 소급해 바꾸지 않는다. 스위치를 끈 뒤에도 이미 코드로 귀속된 주문은 집계에 남는다.
- 끄기 검증: `tests/store-attribution.test.mjs`(꺼짐 → 미귀속, 켬 → 귀속, 다시 끔 → 다음 가져오기부터 미귀속)와 `e2e/store-measurement.spec.ts`.

## 추적 코드

- 종류: 쿠폰(`coupon`), QR(`qr`), POS 태그(`pos_tag`), UTM(`utm`).
- 형식: 혼동 문자(0·O·1·I·L)를 뺀 대문자 영숫자 4~12자. 비워 두면 종류 첫 글자(C·Q·P·U)로 시작하는 8자를 만든다. 직접 정한 코드는 대소문자·공백·하이픈을 무시하고 맞춘다. 코드는 워크스페이스 안에서 하나뿐이다.
- 연결: 캠페인(필수, 이 지점 캠페인이나 같은 브랜드 공통 캠페인), 소재·게시·팔(arm)·유입 채널(선택), 적용 시작일(기본 오늘).
- 게시(publication) 연결: 코드 만들기의 '귀속 게시 · 선택'에서 고른다. 게시는 코드와 같은 캠페인·같은 소재여야 하고(아니면 400, 없는 게시는 404), 게시를 고르면 그 게시의 소재로 묶는다. 게시 상태는 코드를 만들 때가 아니라 주문을 귀속할 때 본다(게시 전에 코드를 만들어 캡션에 넣어야 하므로).
- 소재 이름: 소재 선택과 귀속 보고의 소재별·게시별 표는 소재 제목을 보인다. 제목이 없으면 실행 화면과 같은 대체 라벨(만든 한국 시각 · 첫 사실 줄, 예: '소재 · 9월 23일 14:05 생성 · 주소: 휘경동 377 C107')을 쓴다. 규칙은 한 곳(`lib/execution.ts` `creativeLabel`, `lib/store-attribution.ts`가 다시 내보냄)이고, 소재별 표 이름은 `lib/store-operations-view.ts` `creativeNames`가 만든다. 제목 저장은 실행 쪽(`ExecutionCreative.title`)이 한다.
- UTM 코드에는 `utm_campaign` 값(영문 소문자·숫자·`_ . -`, 60자 이하)이 필요하다. 화면의 복사 버튼은 링크에 붙일 `utm_campaign=…&utm_content=코드`를 복사한다. 다른 종류는 코드만 복사한다.

## 게시 단위 귀속 (A4-2)

같은 소재를 여러 번 게시해도 어느 게시가 주문을 만들었는지 구분한다. 게시마다 코드를 따로 두고, 게시가 실제로 나간 뒤의 주문만 그 게시에 귀속한다.

### 게시별 코드 발급

- 실행 쪽이 발행 초안을 만들 때 코드 종류를 고르면 `issuePublicationCode`(`lib/publication-codes.ts`)로 게시별 코드를 받아 캡션에 넣는다. 캡션 쪽 화면과 규칙은 [브랜드 사실 → 제작 → 발행 → 주문](EXECUTION-LOOP.ko.md)을 따른다. 코드를 고르지 않은 발행의 캡션·해시·승인 흐름은 그대로다.
- 종류는 쿠폰(`coupon`)과 POS 태그(`pos_tag`)만이다. 말이나 계산대 입력으로 확인하는 코드라서다. QR·UTM은 링크·이미지가 필요해 캡션 코드로 발급하지 않는다(점포 화면에서 게시에 직접 묶을 수는 있다).
- 규칙은 점포 화면의 코드 만들기와 같다: 워크스페이스 안에서 유일하고 혼동 문자를 뺀 8자, 캠페인은 그 지점 캠페인이나 같은 브랜드 공통 캠페인, 소재는 그 캠페인·브랜드·지점의 소재, 보관한 지점은 409다. 적용 시작일은 발급한 날(한국 날짜)이고 유입 채널은 SNS · 숏폼(`social`, 발행 채널이 Instagram)이다.
- 멱등: 같은 게시에 캡션 코드(쿠폰·POS 태그)가 이미 있으면 새로 만들지 않고 그 코드를 돌려준다(`publicationCodeFor`). 다른 캠페인·소재·지점으로 다시 부르면 409다.
- 게시 기록은 코드 발급 뒤에 저장될 수 있다. 이미 저장된 게시면 같은 캠페인·소재인지 확인한다. 끝내 저장되지 않은 게시의 코드는 귀속하지 않는다(아래 게시 관문의 '삭제된 게시').
- 권한(관리자)과 쓰기 잠금은 부르는 쪽(실행 API)이 확인한다.

### 게시 관문

- 게시에 묶인 코드로 주문을 귀속하려면 그 게시가 **예약 접수**(`accepted`) 또는 **게시 확인**(`published`)이고, 주문일(한국 날짜)이 게시 예약 시각(`scheduledAt`)의 한국 날짜 이상이어야 한다(`publicationRefusal`). 예: 9월 24일 00:30(한국) 예약은 UTC로 9월 23일이지만 9월 23일 주문은 게시 전 주문이다.
- 적용하는 곳:
  - POS CSV 가져오기의 자동 귀속(스위치가 켜졌을 때만). 관문을 통과하지 못한 코드는 건너뛰고, 같은 칸의 다음 유효 코드가 있으면 그 코드로 귀속한다. 끝내 귀속하지 못한 주문은 미리보기·확정 결과에 사유별로 센다: `beforePublication`(게시 전 주문), `unpublished`(취소·발행 실패처럼 끝난 게시), `pendingPublication`(승인 전·실행 승인·접수 확인 중·접수 여부 미확인·공급자 확인 필요처럼 아직 정해지지 않아 나중에 예약 접수·게시 확인이 될 수 있는 게시). 화면은 '게시 코드로 귀속하지 않음: 게시 전 주문 N건 · 취소·발행 실패 게시 N건 · 게시 상태 확인 전 N건'으로 보인다.
  - 게시 상태 확인 전 게시의 주문이 있으면 확정은 화면의 확인(`allowPendingPublications:true`)이 있을 때만 한다(없으면 409). 저장한 주문은 다시 가져와도 건너뛰므로, 지금 확정하면 그 주문은 게시가 나중에 확인돼도 게시별로 귀속되지 않기 때문이다. 실행 화면에서 게시 상태를 확인한 뒤 가져오는 것이 좋다.
  - 귀속 보고. 이미 코드로 귀속한 주문도 보고서를 만들 때 지금 게시 상태로 관문을 다시 본다(`publicationGateView`). 가져온 뒤 게시가 취소·발행 실패·확인 전 상태로 바뀌었으면 게시·코드·팔별 표에서 빼고, 근거가 가져오기 자동 문구(`추적 코드 … 자동 귀속 · 주문 CSV`) 그대로인 주문은 가져올 때 거절한 주문처럼 미귀속으로 보고 캠페인·소재·채널별 표와 주간 귀속(north-star)에서도 뺀다. 보고서 안내에 '게시 관문 밖 N건'을 적는다. 확인 전 상태였던 게시가 예약 접수·게시 확인되면 다시 센다.
  - 주문 기록 창에서 고칠 때 이어받는 코드 귀속 사본. 보고서와 같은 규칙으로 저장한다: 게시가 지워졌거나 취소·발행 실패거나 주문일이 예약일 전이면 사본을 지우고, 근거가 자동 문구 그대로면 캠페인·소재를 비우고 유입 채널을 미확인으로 되돌려 가져올 때 거절한 주문과 같게 저장한다. 사람이 근거를 새로 적어 저장하면 그 캠페인·소재는 수동 귀속으로 남는다. 게시 상태 확인 전이면 되돌릴 수 있는 상태라 사본을 그대로 둔다. 실험에 연결한 주문은 미귀속(유입 미확인)이 실험 채널과 맞지 않아 409로 막고, 실험 연결을 풀거나 근거를 직접 적게 한다. 그래서 같은 게시 상태면 주문을 고쳤든 안 고쳤든 보고서 집계가 같다.
- 게시가 삭제됐거나 게시의 캠페인·소재가 코드와 어긋나면 캠페인이 삭제된 코드처럼 '쓸 수 없는 코드'(`unavailable`)로 세고 귀속하지 않는다.
- 자동 귀속 스위치가 꺼져 있으면 게시 코드도 기존처럼 미귀속이다(읽은 코드만 남는다). 게시에 묶이지 않은 기존 코드는 관문을 거치지 않고 A4-1과 같게 귀속한다.
- 수동 주문 귀속에는 게시를 직접 넣지 않는다. 게시 귀속은 코드를 거쳐서만 생긴다(주문 기록의 `publicationId` 입력은 저장하지 않는다).
- 게시 관문은 게시에 묶인 코드에만 걸린다. 주문 기록 창의 수동 귀속과, 게시 없이 소재에만 묶은 코드의 자동 귀속은 그 소재가 게시됐는지·주문일이 게시 뒤인지를 보지 않는다(A4-1과 같다). 이유와 넘겨받을 PR은 [범위 밖](#범위-밖)의 `exec-loop-4` (1)에 적었다.

### 게시별 집계

- **귀속 보고** 탭의 '게시별 귀속' 표(`byPublication`)는 게시 코드로 귀속되고 지금 게시 관문을 통과하는 주문만 센다. 줄마다 게시 이름(소재 이름 · 예약 시각(한국) · 게시 상태), 그 게시에 묶인 코드, 귀속 주문 수, 순매출, 공헌이익을 보인다. 지워진 게시는 '게시 <id>'로 보인다.
- 다른 표와 같이 광고비는 배분하지 않고, '귀속≠증분' 표기를 유지한다. 게시별 숫자도 게시가 없었어도 생겼을 주문을 포함한다.
- 검증: `tests/store-publication-codes.test.mjs`(멱등 발급, 다른 브랜드·지점 캠페인 거절, 게시 전 주문·취소·실패 게시 미귀속, 확인 전 게시의 확정 확인(409), 예약 접수·게시 확인 뒤 귀속, 한국 날짜 비교, 게시별 집계 수치, 스위치 꺼짐 미귀속, 게시 없는 기존 코드 불변, 게시 실패 뒤 보고서 재판정, 주문 수정 때 미귀속 저장·수동 근거 유지·확인 전 상태 유지·실험 연결 409, 고친 주문과 안 고친 주문의 같은 집계).

## 수동 추적 프로토콜

코드가 없는 점포에서 쓴다. [결정 13](GROWTH-PLAN.ko.md#대표-결정)에 따르면 ODA의 오픈 주차와 POS 내보내기 열(적립 고객 ID, 쿠폰 코드)은 아직 확인되지 않았다. 오픈이 W10보다 앞서면 이 프로토콜과 F&B 운영 체크리스트로 시작한다. POS 내보내기에 쿠폰 코드 열이 없을 때도 이 프로토콜을 쓴다.

1. 캠페인마다 매장에서 말로 확인할 수 있는 짧은 코드를 정한다. 전단·게시물에 '계산할 때 ○○○○ 코드를 말해 주세요'처럼 적는다. **추적 코드** 탭에 쿠폰이나 POS 태그로 등록해 두면 나중에 CSV 열이 생겨도 같은 코드를 쓴다.
2. 계산할 때 직원이 쿠폰 제시나 코드 언급을 확인하면 POS 주문 메모나 POS 태그 버튼에 코드를 남긴다. 확인하지 못한 주문은 비워 둔다. 짐작해서 적지 않는다.
3. 코드를 확인한 주문만 **주문·비용** 탭의 주문 기록에서 캠페인을 고른다. '유입 확인 근거'에 확인 방법(예: '계산대 구두 확인')을 적는다.
4. 매주 월요일에 지난주(월~일, 한국시간) POS 순매출 합계와 주문 수를 **귀속 보고** 탭의 POS 주간 합계에 입력한다. 합계 출처(예: 'POS 주간 매출 리포트')도 적는다.
5. 입력하지 못한 주는 미통과로 남긴다. 목표는 주간 기록 누락 0주다.
6. 메모·근거 칸에 고객 이름이나 전화번호를 적지 않는다.

## CSV 열 규격

- 형식: UTF-8(BOM 허용) 쉼표 구분 CSV이고 첫 줄이 열 이름이다. 큰따옴표 인용과 인용 안의 쉼표·줄바꿈을 지원한다. 한 파일은 150KB(UTF-8 바이트), 500행, 60열, 칸당 500자까지다. 구조 오류(닫히지 않은 따옴표, 열 수 불일치, 한도 초과)는 파일 전체를 거부한다. 오류의 'N행'은 파일의 실제 줄 번호다(빈 줄·인용 안 줄바꿈을 센다).
- 열 이름은 자유다. **주문 가져오기** 탭에서 열 매핑으로 항목에 연결한다. 흔한 POS 열 이름은 자동으로 고른다(`lib/order-import.ts` `suggestMapping`). 한 열은 한 항목에만 연결할 수 있다.

| 항목 | 필수 | 형식과 처리 | 자동 인식 예 |
|---|---|---|---|
| `orderNumber` 주문번호 | 필수 | 100자 이하. 이 열은 카드번호 검사에서만 뺀다(긴 POS 번호). 휴대폰 번호는 이 열에서도 거부한다. | 주문번호, 영수증번호, 거래번호 |
| `orderedAt` 주문 일시 | 필수 | `2026-09-24`, `2026-09-24 13:05`, `2026/9/24`, `2026.09.24.` 형식이다. 시간대가 없으면 적힌 날짜를 쓰고, `Z`나 `+09:00`이 붙은 ISO 시각은 한국 날짜로 바꾼다. 미래 날짜는 행 오류다. | 주문일시, 거래일시, 날짜 |
| `amount` 결제 금액(할인 후) | 필수 | 원 단위 숫자. 쉼표·`원`·`₩`는 무시한다. 음수와 괄호 금액(취소·환불 행)은 행 오류다. | 결제금액, 실결제금액, 매출액 |
| `discount` 할인 금액 | 선택 | 음수가 아닌 숫자. 비우면 0이다. | 할인금액, 쿠폰할인 |
| `code` 쿠폰·추적 코드 | 선택 | 한 칸에 여러 코드를 `,` `;` `\|` `/`로 나눠 적을 수 있다. UTM 링크 칸은 `utm_campaign`과 `utm_content`를 함께 읽는다. | 쿠폰코드, 쿠폰번호, 추적코드 |
| `channel` 주문 채널 | 선택 | 글자로 출처·방식을 정한다. 배민·쿠팡이츠·요기요·땡겨요는 배달로 본다. '포장·픽업'은 포장, 비어 있으면 POS 홀 주문, 알 수 없는 글자는 기타다. | 주문채널, 판매채널, 주문유형 |
| `customerId` 고객 ID | 선택 | 값이 있는 주문 수만 센다. 값은 저장하지 않고 응답에도 싣지 않는다. | 회원번호, 고객번호, 적립고객ID |
| `newCustomer` 신규 고객 여부 | 선택 | Y/N, 신규/기존(재방문). 그 밖의 값은 행 오류다. 있을 때만 신규 고객 수와 신규 고객당 비용을 계산한다. | 신규고객, 첫주문 |

- 가져온 주문은 결제 완료로 저장하고 환불액은 0이다. 취소·환불은 가져온 뒤 해당 주문 기록에서 고친다. 원가는 비어 있으므로(미확인) 원가를 알면 주문 기록에서 채운다.
- 주문 기록에서 고쳐도 가져오기 기록(`importId`)·할인액·읽은 코드·신규 고객 여부는 남는다. 코드 자동 귀속(`codeAttribution`)은 캠페인·소재를 그대로 둘 때만 남는다. 사람이 캠페인·소재를 바꾸면 수동 귀속이 우선이라 코드·팔 집계에서 빠진다. 게시 코드의 귀속 사본은 [게시 관문](#게시-관문)도 다시 통과해야 남고, 통과하지 못하면 게시 관문 절의 규칙대로 저장한다.
- 중복 방지: 같은 지점·출처·주문일·주문번호는 한 주문이다(기존 주문 장부 id와 같은 기준). 이미 장부에 있는 주문은 '이미 있음'으로 세고 다시 저장하지 않는다. 그래서 같은 파일을 다시 올려도 장부가 늘지 않는다. 파일 안에서 같은 주문이 반복되면 행 오류다.
- 출처가 다른 같은 주문: 출처는 주문 채널 열에서 정하므로 열 매핑만 바꿔 같은 파일을 다시 올리면 출처가 달라진다. 같은 주문일·주문번호의 주문이 다른 출처로 이미 있으면 미리보기에 그 건수와 행 번호를 보이고, 화면에서 별개 주문임을 확인해야 확정한다(`allowSourceConflicts:true`, 없으면 409).
- 미리보기 → 확정: 미리보기는 저장하지 않는다. 저장 가능·이미 있음·오류 행·자동 귀속·미귀속 건수, 게시 관문에서 빠진 건수(게시 전 주문·취소/발행 실패 게시·게시 상태 확인 전), 앞 20건 표본, 앞 50건 오류 사유를 보여 준다. 확정은 원자적이어서 오류 행이 하나라도 있으면 아무것도 저장하지 않는다. 가져오기마다 파일 이름·건수·매핑·스위치 상태·실행자를 `order_import` 기록으로 남긴다. CSV 원문은 저장하지 않는다.

## 개인정보 원칙

- 고객 ID 열은 원문을 저장하지 않는다. salted hash를 둘지는 결정 11 이후에 정하므로 이번에는 해시도 저장하지 않고 식별 가능한 주문 건수(`identifiableOrders`)만 센다.
- 휴대폰 번호(`010-1234-5678`, `+82 10 …` 등)가 어느 열에든(주문번호 열 포함) 있거나, 카드번호로 보이는 13~19자리 숫자열이 주문번호 열을 뺀 어느 열에든 있으면 파일 전체를 거부한다. 매핑하지 않은 열도 검사한다. 오류 문구에는 열 이름만 싣고 값은 싣지 않는다. 가려진 번호(`010-****-5678`)와 사업자번호처럼 짧은 번호는 통과한다.
- 거부되면 POS에서 그 열을 빼고 다시 내보낸다. 메모·근거 칸에도 이름·전화번호를 적지 않는다.
- 재방문율·고객별 분석은 하지 않는다. 가명 고객 키와 동의 원장은 A5(결정 11·12, 법률 검토 뒤)에서 다룬다.
- 공개 저장소에는 실제 주문 CSV나 운영 산출물을 올리지 않는다.

## 완전성 검사와 north-star

- 주는 한국시간 월요일에 시작해 일요일에 끝난다. POS 주간 합계는 끝난 주에만 입력할 수 있고, 주마다 1건을 버전으로 고쳐 쓴다. 기준 주(incrementality-lite 비교용)도 같은 표에서 '기준 주'로 보이고 합계를 입력할 수 있다.
- 조회 기간은 182일(26주), 기준 기간은 84일(12주)까지다. 주간 장부 합계는 주문 행을 읽지 않고 일별 SQL 합계로 계산하므로, 5,000건 조회 상한은 조회 기간의 주문 행(코드·팔·소재·캠페인·출처별 표)에만 걸린다. 넘으면 조회 기간을 좁힌다.
- 장부 합계는 그 주 장부에 있는 모든 주문(출처 무관)의 순매출(결제액 − 환불액)과 유효 주문 수다.
- 판정:
  - 통과: 장부 순매출이 POS 순매출 합계와 1% 이내다. POS 주문 수를 입력했다면 주문 수도 1% 이내여야 한다. POS 합계가 0이면 장부도 0이어야 한다.
  - 미통과: 위 조건을 벗어나면 서버가 차이를 사유로 적는다.
  - 미입력: POS 합계가 없으면 통과로 보지 않는다.
- north-star는 [성장 계획](GROWTH-PLAN.ko.md#kpi)의 '귀속 근거가 있는 주간 주문·공헌이익'이다. 완전성 검사를 통과한 주의 귀속 주문 수와 공헌이익만 더한다. 미통과·미입력 주의 주문은 장부에 남지만 north-star에는 넣지 않는다. 통과한 주가 없으면 측정하지 않은 것으로 본다.
- 귀속 주문은 캠페인·소재·유입 채널 중 하나가 연결된 유효 주문이다(수동·자동 귀속 모두). 공헌이익은 원가가 모두 확인된 주문만 계산한다. 하나라도 모르면 미확인으로 두고 추정하지 않는다. **귀속 보고** 탭의 '변동비율(0~1)' 칸(`variableCostRate`)에 값을 넣은 경우만 추정하고, 표에는 추정한 건수를, north-star 카드에는 추정 비율을 표시한다.
- 단위경제: 코드·팔·소재·캠페인·출처별로 주문 수·순매출·공헌이익·신규 고객을 보인다. 캠페인·팔·소재 표는 캠페인 ID 대신 캠페인 제목을, 소재 표는 소재 ID 대신 소재 이름을 보인다. 게시별 표는 [게시별 집계](#게시별-집계)를 본다. 광고비는 채널별 비용 기록(주문 장부의 광고·제작 비용)으로만 이어 채널별 표에서 주문당 비용과 신규 고객당 비용을 계산한다. 코드·팔·캠페인·출처에는 광고비를 나누어 배분하지 않는다.

## incrementality-lite의 한계

- 계산: 조회 기간의 주 평균(기본 지표는 주문 수)을 기준 기간(기본값은 조회 시작 주 앞 4주)의 주 평균과 비교한다. 두 기간 모두 완전성 검사를 통과한 주만 쓰고, 빠진 주는 경고로 알린다.
- 화면과 보고서는 항상 이 문장을 먼저 보인다: 귀속≠증분: 추적 코드로 귀속된 주문은 캠페인이 없었어도 생겼을 수 있습니다. 귀속 수치는 캠페인의 인과 효과를 증명하지 않습니다.
- 한계:
  - 대조군이 없는 단순 전후 비교다. 계절·요일 구성·날씨·공휴일·주변 행사·다른 판촉·가격 변경의 영향을 분리하지 않는다.
  - 오픈 직후처럼 추세가 있는 기간에는 변화가 캠페인 때문인지 알 수 없다.
  - 표본이 작다. 기준 주가 2주 미만이면 경고하고, 귀속 주문이 증가분보다 많으면 경고한다(귀속 일부는 원래 올 손님이다).
  - POS 합계를 입력하지 않은 주는 빠지므로 비교할 주가 없으면 변화는 미확인이다.
- 쓰는 법: 계속·중단 판단의 방향 신호로만 쓴다. 예산 결정은 사람이 하고, 검증 없는 광고 예산 변경은 하지 않는다(`AGENTS.md` 금지 항목). 더 강한 근거가 필요하면 같은 캠페인 안에서 팔(arm)을 나누거나 지점·기간을 엇갈려 비교한다.

## 범위 밖

A4-1은 점포 장부 쪽 귀속 집계(코드·팔·소재·캠페인·출처별, 주간 완전성, north-star)를, A4-2는 게시 코드를 거친 게시 단위 귀속을 해결했다. 담당 finding의 처리와 넘겨받을 PR은 아래와 같다.
