# 브랜드 심층 조사 결과 검증

심층 조사(`investigation` 단계)의 HERMES 응답을 검증하는 규칙이다. 파서는 `lib/deep-research-server.ts`의 `parseDeepText`(JSON 파싱 포함)와 `parseDeepReport`다. 결과 저장과 수리 턴은 [신뢰성 문서](RELIABILITY.ko.md#a7-조사-투자-회수-부분-구제와-수리-턴-a7_repair_turn)에 있다.

## 부분 구제

조사는 전체 토큰의 87%를 쓴다(`docs/observations/2026-09-23-live-run.md`). 예전에는 항목 하나만 틀려도 422로 결과 전체를 버렸다. A7부터는 틀린 원소만 빼고 나머지를 살린다. 추가 호출이 없는 기본 동작이다.

- **항목 단위 오류는 구제한다.** 목록 원소 하나의 형식·범위·참조 오류는 그 원소만 뺀다. 목록의 최대 개수(예: `sources` 40개, `cases` 30개, `review.unresolved` 12개, `review.followups`는 조사 계획의 `maxFollowups`개)를 넘은 뒤쪽 원소도 ‘최대 N개를 넘어 뺐습니다.’로 하나씩 뺀다. 대상 목록은 `sources`, `access`, `cases`, `customerSignals`, `competitors`, `review.claims`, `review.followups`, `review.unresolved`, `diagnosis.opportunities`, `diagnosis.questions`다. 원소가 null·원시값이어도 TypeError가 아니라 같은 항목 단위 오류로 처리한다(`security-ops-11` 잔여 해소).
- **연쇄 제거.** 뺀 신규 출처를 가리키던 원소도 함께 뺀다. 사유는 ‘근거 출처가 빠져 함께 뺐습니다.’다. 접근 기록이 없는 신규 출처와 최대 개수를 넘은 신규 출처도 빠지고, 그 출처를 가리키던 원소도 같은 규칙으로 빠진다.
- **출처 번호 충돌은 가리지 않고 뺀다.** 같은 번호를 다른 URL에 쓴 출처(신규끼리, 또는 신규와 입력 자료)는 어느 쪽 근거인지 알 수 없다. 그 번호의 신규 출처를 모두 빼고, 그 번호를 인용한 원소(접근 기록·관찰·경쟁·진단 근거 등)도 ‘출처 번호가 겹쳐 근거를 가릴 수 없어 뺐습니다.’로 뺀다. 먼저 남은 출처나 확인된 입력 자료로 근거를 옮겨 붙이지 않는다. 입력 자료와 번호·URL이 모두 같은 재선언은 뒤쪽 출처만 빼고 인용은 입력 자료를 가리킨다.
- **중복은 뒤의 원소를 뺀다.** 같은 출처의 접근 기록, 같은 출처나 번호의 콘텐츠 표본, 같은 이름의 경쟁·대안이 해당한다. 앞의 원소는 남는다.
- **진단 근거(`diagnosis.sourceIds`)는 뼈대다.** 뺀 출처만 목록에서 걸러낸다. 처음에 있던 근거가 모두 빠지면 구제하지 않고 뼈대 오류로 올린다. 처음부터 근거가 없던 진단은 예전처럼 받고 품질 이슈로 남긴다. 실험 과제가 모두 빠진 경우도 뼈대 오류가 아니라 품질 이슈(`needs_data`)다.
- **출처나 진단 근거를 뺐으면 검토 가능으로 올리지 않는다.** 진단 문장은 뺀 근거에 기댔을 수 있다. `sources`나 `diagnosis.*`에서 뺀 항목이 있으면 품질 이슈 ‘형식·근거 검증에서 뺀 항목 N개가 있습니다. 진단 문장이 뺀 근거에 기대지 않는지 원문과 대조하세요.’를 더해 `needs_data`로 둔다.
- **살아남은 신규 출처의 번호는 원래 위치 기준 그대로다**(`<조사 id>-e<원래 순번>-0`). 저장 상태는 기존 규칙대로 `candidate`다. 사람 확인 게이트(`data-truth-10`)는 바뀌지 않는다.
- **정상 보고서의 결과는 바뀌지 않는다.** 구제 도입 전 파서와 같은 합성 보고서의 출력이 바이트 단위로 같다(생성 시각 제외, `tests/research-salvage.test.mjs`).

## 뼈대 오류

아래 오류는 구제하지 않는다. `DeepReportShapeError`(`ApiError` 422)로 던지고 사용자용 한국어 문구(`message`, 첫 오류)는 예전 그대로다. 서로 독립인 뼈대 검사(단계 기록, 각 목록의 형식, 진단 근거, 진단 필수 필드·질문 형식)는 모두 돌려 `errors`에 모은다. 목록 형식이 깨져 뒤따르는 오류(예: 출처 목록이 깨져 진단 근거를 찾지 못함)는 따로 세지 않는다. 수리 턴은 이 오류만 고칠 대상으로 보고 `errors` 전부를 넘긴다.

- JSON 객체가 아닌 응답(`parseDeepText`)
- 응답 크기 700,000바이트 초과
- 목록이 배열이 아니거나 최대 개수의 두 배를 넘음(크기 한도. 예: `sources` 80개, `review.unresolved` 24개 초과)
- 여섯 조사 단계 기록의 누락·순서 오류, 단계 요약 형식 오류. 예전에 400이던 단계 요약 오류도 422가 된다. 조사 기록에는 문구만 남으므로 화면은 같다.
- 진단 필수 필드(요약·포지셔닝·고객·니즈·강점·문제·한계)와 질문 목록 형식, 입력·신규 출처에 없는 진단 근거
- 진단 근거가 모두 빠짐(‘진단이 참조하는 출처가 모두 빠졌습니다.’)

저장된 조사 계획이 없으면 응답을 고쳐도 풀리지 않는다. 그래서 일반 `ApiError`(422)로 둔다.

## 구제 기록과 화면

- 파서 반환값의 `salvage`는 `{dropped:[{section,index,id?,reason}], kept:{목록 이름: 남은 개수}}`다. `index`는 원래 응답의 위치다. `id`는 출처·콘텐츠 표본 번호가 짧은 영숫자(`^[\w-]{1,80}$`)일 때만 남긴다.
- `reason`은 검증 규칙의 사용자용 문구만 쓴다. 뺀 원소의 원문, 내부 예외 문구, 스택은 남기지 않는다.
- 조사 기록(`brand_research`)의 `salvage`에도 같은 모양 그대로 뺀 원소마다 사유를 모두 저장한다(상한 없음. 목록 상한이 있어 수백 건, 수십 KB 안이다). 타입은 `lib/archive.ts`의 `ResearchSalvage`다.
- 화면: 뺀 항목이 있을 때만 조사 결과 패널과 ‘조사 기록’ 탭에 ‘살린 출처 N · 뺀 항목 M’ 접기 영역이 보인다. 펼치면 뺀 항목 전부의 목록 이름·순번·사유를 볼 수 있다(`app/deep-research-panel.tsx` `SalvageNote`).
- 수리 응답(`a7_repair_turn`)은 같은 파서를 거치되, 원래 응답에 나온 URL(`responseUrls`)에 없는 신규 출처를 ‘수리 응답에 원래 없던 출처라 뺐습니다.’로 빼고 인용을 연쇄로 뺀다.

## 테스트

- `tests/research-salvage.test.mjs`: 정상 보고서 불변(바이트 비교), 잘못된 표본 1개, 잘못된 출처의 연쇄 제거와 품질 이슈, 접근 기록 없는 출처, 중복, null·원시값 원소, 뼈대 오류 구분과 오류 목록 수집, 최소 개수 붕괴, 사유에 원문·스택 없음, 사유 전부 보관, 최대 개수 초과분 제거, 출처 번호 충돌을 확인한다.
- `tests/validate.test.mjs`: 좁히기 헬퍼의 항목 단위 사유와 뼈대 오류 구분을 확인한다.
- `tests/archive.test.mjs`: 시청 기록·검색 요약·중복 표본·중복 URL 위반이 구제되는지, 진단 근거를 뺀 보고서가 검토 가능으로 올라가지 않는지 확인한다.

근거는 모두 mocked(합성 보고서)다. 유료 모델·HERMES 실호출은 없다.
