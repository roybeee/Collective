# 상품 리서치·MD 에이전트 운영 문서 (P4·P5 서버)

결론: 상품 리서치는 공식 API와 운영자·계약 데이터 가져오기로 시장 지표를 모으고(수집), 결정형 점수표로 평가하고(재계산), 근거를 인용한 선정 메모를 만든 뒤(결정형 또는 AI 팀 상품 MD), 대표·관리자가 승인한 상품만 성장2 캠페인의 시장 근거로 넘긴다. 발주·결제·가격 승인·공급자 연락은 하지 않는다(`mayOrder:false`).

- 계획: [PRODUCT-RESEARCH-PLAN.ko.md](PRODUCT-RESEARCH-PLAN.ko.md). 이 문서는 구현된 서버의 운영 기준이다.
- 코드: `lib/product-research/server*.ts`, `lib/product-research/md-prompt.ts`, `app/api/product-research/route.ts`, 워커 큐 `lib/research-worker.ts`(`product_research`).
- 검사: `tests/product-research-server.test.mjs`, `tests/product-research-server-ops.test.mjs`(상한·잠금·재시도·격리·자사 판매·관문), `tests/product-research-server-scale.test.mjs`(스냅샷 3,000개·점수표 5만 판 화면 응답), `tests/product-research-server-backtest.test.mjs`(90일 일별 스냅샷 백테스트·출처별 읽기·생존 편향), `tests/product-research-server-round2.test.mjs`(격리 단위·묶음 보정·실행 시간 상한·잠금 갱신·소싱 후보 초안·출시 뒤 결과) (mocked: 메모리 SQLite, 공급자·HERMES fetch 스텁, 주입한 시계, 실제 네트워크 0).
- 운영 보강 코드: `lib/product-research/server-ops.ts`(재계산 감싸기·자사 판매·이상치 격리·점수표 색인·신선도·주간 MD 리포트).

## 3. 외부 호스트·쿼터·근거

두 가지를 구분한다. **계획 한 번**은 하루 계획(작업자)과 즉시 수집이 한 번 도는 크기이고, **앱 하루 상한(원장)**은 쿼터 원장(`pr_quota`)이 호출 전에 원자적으로 막는 하루 총량이다(`lib/product-research/collectors/quota.ts` `APP_DAILY_CAPS`, 공급자 단위, 이 표와 `tests/product-research-server-ops.test.mjs`가 같은 값을 확인한다). 공급자 한도가 공개되지 않은 출처도 보수적인 상한으로 막는다.

| 출처 | 호스트 | 계획 한 번 | 앱 하루 상한(원장) | 공급자 쿼터 | 근거 |
|---|---|---|---|---|---|
| 네이버 검색광고 키워드 도구 | `api.searchad.naver.com` | 키워드 40개(호출당 5개, 8회) | 200회 | 미공개 | 공식 API, 광고주 키 서명 |
| 네이버 데이터랩 검색어 트렌드 | `openapi.naver.com` | 묶음 40개(호출당 5개, 8회), 최근 104주 주간 | 900회 | 1,000회 | 개발자센터 공식 API |
| 네이버 데이터랩 쇼핑인사이트 | `openapi.naver.com` | 계획에 없음 | 0(호출 안 함) | 1,000회 | 개발자센터 공식 API |
| 네이버 쇼핑 검색 | `openapi.naver.com` | 키워드 20개 | 2,000회 | 25,000회 | 개발자센터 공식 검색 API |
| YouTube Data API v3 | `www.googleapis.com` | 발견 3회(`search.list` 100단위씩) + 추적 영상 200개(`videos.list` 50개씩) | 9,000단위(태평양 날짜) | 10,000단위 | 공식 API |
| 쿠팡 파트너스 | `api-gateway.coupang.com` | 식품(1012) 베스트 1회 | 100회 | 승인 조건에 따름(미공개) | 공식 Open API(HMAC) |
| 운영자·계약 가져오기 | 없음(파일) | 2MB·2,000행/파일, 기준일은 한국 날짜로 오늘~14일 전 | 0(자동 호출 없음) | — | 쿠팡·무신사·올리브영 랭킹은 자동 수집 금지(robots·403), 계약 데이터는 계약 전 내보내기 파일만 |

- 호출 전에 쿼터 원장에 단위를 원자적으로 예약한다. 앱 하루 상한을 넘게 되면 호출하지 않고 그 출처를 오늘 건너뛴다(쿼터 초과 0). 입력 오류처럼 호출 전에 막힌 경우만 되돌린다.
- 하루에 쓰는 양: 작업자의 하루 계획 1번 + 즉시 수집(`collect_now`) 한국 날짜 하루 3번까지. 즉시 수집은 오늘 계획을 이어 가거나(끝났으면 새로 한 번) 고른 출처만 돌며, 어느 경우든 원장의 남은 상한 안에서만 호출한다. 4번째부터는 409.
- 출처 연결(`connect_source`)은 저장 전에 가장 싼 실제 호출 1번으로 키를 확인한다: 검색광고 힌트 1개, 데이터랩 7일 1묶음, YouTube 공개 영상 1개 `videos.list`, 쿠팡 검색 1개. 결과는 저장하지 않고 쿼터만 센다. 계약 데이터는 고정 호스트가 없어 형식만 확인한다.
- 법적 근거·약관 확인은 대표 결정 D5(법무 검토) 대상이다. 이 문서는 법률 판단이 아니다.

## 4. 흐름

1. **수집**: 한국 날짜로 하루 1번 계획을 세우고 워커 tick마다 12단계씩 이어 간다. 소유자는 `collect_now`로 바로 30단계까지 실행할 수 있다(하루 3번). 한 출처의 실패는 그 출처만 멈추고 다른 출처는 계속한다. 계획을 다 돌면 재계산한다.
   - **실행 시간 상한·잠금 갱신**(평가 2회차 M4): 잠금(`${owner}:product-research`)은 120초 뒤 만료되는데 단계 하나가 최대 20초라 12·30단계가 넘을 수 있었다. 한 번 실행은 90초(`RUN_TIME_BUDGET_MS`, 주입한 시계 `deps.now`로 잰다)를 넘으면 남은 단계를 두고 진행 위치를 저장한 뒤 멈추고(`stoppedAt`), 다음 tick이 이어 간다. 단계마다 잠금 만료를 120초 뒤로 갱신하고, 잠금을 잃었으면(만료 뒤 다른 실행이 가져감) 수집 상태를 저장하지 않고 멈춘다(작업자는 idle, 즉시 수집은 409). 즉시 수집이 시간 상한으로 멈추면 재계산은 작업자가 계획을 마칠 때 한다.
   - **30일 성공률**: 정상 응답을 받아 스냅샷 저장까지 끝난 호출만 성공으로 센다(저장 실패는 호출만 센다).
   - **일시 오류 재시도**: 네트워크·시간 초과·5xx·429는 그 출처만 5분(두 번째는 20분) 물러났다가 다음 작업자 tick에서 다시 시도한다(`pr_collect_state.nextAttemptAt`). 한 출처가 한국 날짜 하루 3번 실패하면 오늘은 멈추고 내일 다시 한다. 인증 실패·하루 쿼터 소진·허용 밖 호출은 바로 오늘 멈춘다.
   - **경보**: 성공할 때까지 이어지는 출처별 실패와 격리 대기 관측을 GET `alerts:{sourceId,message,since}[]`로 보여 준다. 홈 '오늘의 안건'(`lib/agenda-server.ts`, 레인 A)은 캠페인 범위 항목만 다루고 출처 경보를 받을 확장 지점이 없어 넣지 않았다(화면 응답 필드만).
   - **주간 MD 리포트**: 작업자가 그날 계획을 마친 뒤 한국 날짜 기준 그 주(월요일 시작)에 아직 없으면 한 번, 도입 검토·관찰 상위 10개(선정 금지 제외)로 결정형 메모(모델 호출 없음, 질문 `주간 MD 리포트`)를 `pr_brief`로 저장한다. 후보가 없으면 만들지 않고 사유를 `weeklyReport.reason`에 남긴다.
2. **재계산**(`recompute`, 외부 호출 없음, `server-ops.ts refreshScores`): ① 자사 판매 스냅샷 → ② 이상치 격리 → ③ 재계산 → ④ 소싱 연결 보존 → ⑤ 점수표 색인 → ⑥ 데이터랩 보정 보고·출시 뒤 결과(수집 상태에 저장).
   - ① **자사 판매(`own_sales`, internal)**: 성장 주문 품목(`growth_order_line`)과 지점 주문(`store_order`)에서 주문 ID·SKU·상품명·결제/환불 배분·주문일·상태만 읽어(고객 정보 없음, 읽기 전용) SKU·주(월요일 시작, 한국 날짜)별 `own_orders`(주문 수)·`own_revenue`(결제−환불, 배분이 빈 품목이 있으면 null)를 만든다. 진행 중인 이번 주·취소 주문은 뺀다. 합계가 바뀌었을 때만 새 스냅샷을 저장한다. 점수표가 이 시계열을 쓰는 것은 분석 계층(점수 입력) 몫이다.
   - ② **이상치 격리**: 시계열의 마지막 관측이 직전 8개 점의 중앙값에서 강건 z 5배를 넘으면(척도 = max(1.4826×MAD, |중앙값|×10%, 1)) 그 관측을 `pr_quarantine`에 남기고, 사람이 `clear_quarantine`(사유 5자 이상)으로 해제하기 전까지 점수 재료에서 뺀다(스냅샷은 그대로). 누적값(영상 조회수·리뷰 수)과 순위·평점·경쟁 지수는 검사하지 않는다. 한 번 해제한 관측(같은 출처·대상·지표·기간 끝)은 다시 격리하지 않는다.
     - 격리 단위(평가 2회차 M1)는 관측 한 점(스냅샷·대상·지표·기간 끝 `periodTo`)이다. 데이터랩 104주 시계열 전체를 빼지 않는다. `periodTo`가 없는 옛 행은 예전처럼 그 스냅샷의 대상·지표 전체를 뺀다.
     - 상대값(데이터랩 검색 추세·쇼핑 클릭 추세)의 급등은 같은 키워드의 검색광고 30일 실측이 반박할 때(실측은 평소 수준, 강건 z ≤ 2)만 격리(`active`)하고, 실측도 함께 올랐거나 대조할 실측이 없으면 빼지 않고 표시(`flagged`)만 한다(진짜 상승을 숨기지 않는다). 격리한 상대값 기간은 다음 날 같은 주를 다시 받은 스냅샷에서도 빼고, 같은 기간을 날마다 새로 격리·표시하지 않는다. GET `anomalyFlags`(최대 50)가 표시만 한 관측, `quarantines`가 격리한 관측이다.
   - ③ 최근 120일 스냅샷을 출처별 계획으로 읽는다(평가 2회차 H4, `server-pipeline.ts recomputePlan`): 데이터랩은 묶음마다 가장 최근 1개(104주 이력을 싣는다), 자사 판매는 최신 1개, 검색광고(쓰는 지표 `search_volume_month`·`ad_competition`만 SQL에서 골라 읽음)·쇼핑·YouTube·순위 출처는 120일 창 안 출처별 상한(1,200·900·900·출처마다 600). 예전처럼 전 출처 합산 최신 3,000개로 자르지 않아(하루 44개 안팎이면 68일) 12주 순위 기울기가 잘리지 않는다. → 시계열 → 키워드 묶음(최대 500개) → 상품 매칭(자동 목록 최대 400개, 0.95 이상만 자동 병합) → 점수표 w1. 영상 조회수는 키워드로 발견한 영상들의 증가분을 더한 합성 누적 시계열로 넣는다(점마다 `videos.list` 스냅샷을 가리킴, 메모 주장에는 쓰지 않음).
     - **데이터랩 묶음 보정**(평가 2회차 M3): 데이터랩 묶음 값은 묶음 키워드 검색량의 합이라, 상대값 → 검색량 보정의 기준점도 묶음에 넣어 요청한 키워드(스냅샷 요청 범위 `keywordGroups`)의 검색광고 30일 실측 합으로 잡는다(같은 날 값이 모두 있는 날만 더한다, 빠진 키워드를 0으로 보지 않음). 합에 든 키워드는 수요에 다시 더하지 않는다. GET `calibration:{at,groups,mape,rows:[{groupId,label,error}]}`은 마지막 재계산의 묶음별 검증 오차(겹치지 않는 달력 월 기준점)와 평균 절대 백분율 오차다. 기준점이 모자라면 `error`·`mape`는 null.
     - 연결한 소싱 견적을 손익 입력으로 바꿀 때 생긴 메모(견적 단위가 묶음, 세금 기준 미확인 등)는 수익성 하위 점수 설명 끝에 `견적 참고:`로 남는다(점수표 입력 해시에도 들어간다).
   - ⑤ **점수표 색인**: 상품별로 현재 판과 계산 날짜마다 가장 늦은 판 요약을 최근 30개까지 `pr_score_index`에 둔다(하루에 여러 판이 생겨도 지난주 판이 남는다). 화면 응답은 이 색인으로 '지난주'(6일 이상 앞선 가장 최근 판) 점수를 찾고, 점수표 전체를 읽지 않는다.
   - **신선도**: GET `freshness:{sourceId,successRate30d,calls30d,lastOkAt,quarantined}[]`. 성공률 = 최근 30일 원장의 정상 응답 수 ÷ 호출 수(호출이 없는 출처는 null). `rankingStatus:{sourceId,lastImportedAt,thisWeek}[]`는 랭킹 가져오기 출처별 이번 주(한국 날짜, 월요일 시작) 가져오기 여부다.
3. **선정 메모**(`generate_brief`): `template`은 결정형. `model`은 HERMES 연결이 있어야 하고(없으면 409), 관측표(최근 행과 바로 앞 기간 행)만 보낸다. 모델은 주장 문장을 쓰지 않고 구조 `{productId,row,kind,compareRow?}`(kind: value·change·rank·price·count)로 관측표 행만 고른다. 주장 문장은 서버가 그 행의 값·단위·기간으로 고정 틀에서 만든다(결정형 메모와 같은 틀·같은 인용 검사, 변화 방향도 서버가 값으로 정한다). 모델이 쓰는 글은 짧은 요약·리스크뿐이며, 금지 목록이 아니라 허용 어휘(정해 둔 낱말·조사·어미와 고른 상품 자신의 이름)만 통과한다. 그래서 숫자·글자로 쓴 수·단위·방향 말·최상급·인증 말·권고 말은 자유 글에 쓸 수 없고, 키워드·목록 제목으로 금지 말을 세탁할 수도 없다. 권고는 `recommendation` 칸으로만 내고 점수표 판정을 넘지 못한다. 하나라도 어긋나면 저장하지 않고 409와 근거 없는 목록을 돌려준다. 같은 요청 번호로 다시 보내도 모델을 다시 부르지 않는다. 약 20초 안에 끝나지 않으면 `pending:true`를 돌려주고, 같은 요청 번호로 다시 보내면 이어서 확인한다. 판을 올리기 전에 시작한 대기 작업의 v3 꼴 주장은 확인만 하고 글은 버린 뒤 서버 틀 문장으로 저장한다. 프롬프트는 `lib/product-research/md-prompt.ts`, 판 `pr-md-brief-v4`(구조 주장·서버 틀 문장·자유 글 허용 어휘·자료 칸 주입 방어·권고는 점수표 판정 이하). 레인 Q가 v4를 프롬프트 레지스트리에 '상품 MD' 단위로 등록해야 한다(이 레인은 레지스트리를 고치지 않는다, v3 등록은 v4로 바꿔야 한다).
4. **결정**(`decide`): 현재 점수표 판에만, 사유 5~500자와 함께. 승인 관문: 선정 금지(`blocked`) 점수표는 409, 검토 필요(`needsReview`) 점수표는 ① 그 판에 저장한 최신 리스크 체크리스트(`save_risk_review`, 항목 1~30개)가 서버 필수 항목을 모두 확인했고 확인하지 않은 항목이 없거나 ② 위험 확인 표시(`riskAcknowledged:true`)와 확인한 위험(`review.terms`)을 적은 사유(`analytics/score.ts reviewApprovalError`)여야 승인된다. 아니면 409. 저장한 체크리스트에 확인하지 않은 항목이 있으면 ②로 넘어가지 않고 409(항목 이름을 알려 준다).
   - **필수 항목**(평가 2회차 H1): 서버가 점수표의 `review`(리스크 높음 항목)에서 만든다. `id`는 규칙 id(규칙과 사유가 1:1일 때, 아니면 `review_번호`), `text`는 그 위험 사유 문장. GET `riskChecklists:[{scoreCardId,items:[{id,text}]}]`. 체크리스트 항목 `{rule,checked,ruleId?}`의 `rule`이 필수 항목 text·id와 같거나 `ruleId`가 필수 항목 id면 그 항목으로 센다. 모르는 `ruleId`는 400. 그 밖의 항목은 운영자 추가 항목으로 저장만 하고(`ruleId:null`) 승인에 세지 않는다(확인하지 않았으면 승인을 막는다). 화면이 보낸 자유 문장 하나(`[{rule:'x',checked:true}]`)로 관문을 열 수 없다. 승인 때 필수 항목은 저장한 문장이 아니라 점수표에서 다시 만든다.
5. **넘기기**(`handoff`): 승인한 최신 결정만, 같은 소유자의 보관 전 캠페인·캠페인 판 일치·전역 중단 꺼짐일 때(전역 중단이면 409, 아무것도 쓰지 않음). 한 batch로 ① 시장 신호 1개(`sourceType:'market'`, 제목 `상품 리서치: <상품>`, 요약은 인용 관측 문장만), ② 그 신호를 잇는 고객 기회 초안 1개(`growth_need`, 성장 화면의 니즈 형식 검사를 통과해야 하며 상황·원하는 결과·장애물·다음 행동에 `초안 — 사람이 채움`), ③ 각각의 성장 이력, ④ 결정의 넘기기 연결(`signalId`·`needId`)을 쓴다. 카탈로그·오퍼·주문은 만들지 않는다. 신호·니즈에 `productResearch{decisionId,scoreCardId,productId,snapshotIds}` 계보를 남긴다.
   - **관측 시각**: 가져오기 근거는 파일 기준일, 수집 근거는 관측 기간의 끝을 한국 날짜 0시로 본다(가져온·수집한 시각이 아니다). 관측이 30일보다 오래된 근거는 인용하지 않고, 남는 근거가 없으면 409. 신호의 관측 시각은 인용한 근거 중 가장 오래된 것, 유효기한은 +30일이다.
   - 출처 주소는 상품 목록의 공개 https 주소(쿼리 없는 것), 없으면 요청의 `sourceUrl`이 필요하다(409로 안내). 넘긴 신호는 성장 화면에서 고칠 수 없다(니즈 초안은 사람이 고쳐 채운다).
   - **소싱 연결**(`link_sourcing`·`unlink_sourcing`): 상품을 같은 소유자·브랜드·캠페인의 소싱 후보(`growth_sourcing_candidate`)와 잇고 후보 판을 `ResearchProduct.sourcing{campaignId,candidateId,candidateVersion}`에 둔다. 재계산이 상품을 다시 써도 연결은 보존한다.
   - **소싱 후보 초안**(평가 2회차 M6): 같은 batch에 성장2 소싱 후보 형식(`lib/growth-sourcing.ts parseCandidateInput`)을 그대로 통과하는 초안 1개를 만든다(`status:'draft'`, `mayOrder:false`, 원가·MOQ·납기·배송비 null, 세금 기준·단위 미확인, 공급처 `unassigned`, 계보 `productResearch`) + 소싱 이력 1행. 후보는 카탈로그 상품을 가리켜야 해서 요청의 `catalogId`(이 캠페인·브랜드의 것, 아니면 404) 또는 캠페인 카탈로그 상품이 하나일 때만 만들고, 아니면 만들지 않고 까닭을 요청 기록(`candidateSkipped`)에 남긴다(카탈로그는 만들지 않는다). 상품에 이 캠페인의 소싱 연결이 이미 있으면 만들지 않고, 연결이 없으면 초안을 잇는다. 결정의 넘기기 연결에 `candidateId`·`at`(넘긴 시각)을 더한다.
   - **출시 뒤 결과**(평가 2회차 M5, 재계산 ⑥): 넘긴 결정 → 소싱 후보(초안 또는 상품 연결) → 카탈로그 상품 SKU → 성장 주문 품목·지점 주문으로 넘긴 시각부터 4·8·12주 주문 수·수량·순매출(결제−환불)을 센다(취소 주문 제외, 진행 중인 창은 `complete:false`). SKU를 알 수 없으면 값은 null과 까닭, 주문 장부가 아예 없으면 null, 장부에 그 SKU 주문이 없으면 0. GET `launchOutcomes:[{decisionId,productId,campaignId,handedOffAt,sku,reason,windows:[{weeks,complete,orders,units,revenue}]}]`(최근 넘긴 결정 200개). 운영자가 SKU를 직접 잇는 작업은 없다.
6. **백테스트**(`run_backtest`): 화면은 정답 기준을 퍼센트로 보내고 서버가 비율로 바꾼다. 기준 시점 이전 4주 + 관측 기간보다 이력이 짧으면 숫자 없이 사유를 남긴다.
   - **읽기 계획**(평가 2회차 H4, `backtestPlan`): 기준 시점 추정 E = 가장 늦은 스냅샷 − 관측 기간. 검색광고 E−75일~E+2일, 쇼핑 E−63일~, YouTube E−49일~, 순위 출처 E−14주~끝, 데이터랩은 묶음마다 최신 1개(정답용) + E−3일 이전에 받은 최신 1개. 90일 일별 스냅샷에서도 12주 백테스트가 후보와 '현재 1위' 기준선 값을 가진다.
   - **생존 편향 차단**(평가 2회차 H3, `asOfCut`): 오늘 받은 데이터랩은 104주 이력을 싣기 때문에, 기간 끝만 보면 지금 인기라 추적을 시작한 키워드가 과거 기준 시점의 후보가 됐다. 후보는 그 대상(키워드·목록)이 처음 수집된 시각이 기준 시점 이하인 것만이고, 특징은 같은 (대상·지표·출처)를 기준 시점 이전에 받은 스냅샷이 있으면 그것만 쓴다. 없을 때만 뒤에 받은 스냅샷의 과거 구간(소급 이력)을 쓰고 그 수를 `universe.notes`에 적는다. 자료를 모두 오늘 처음 받았다면 후보가 없어 숫자 없이 사유를 남긴다. 운영자 고정 정답셋은 아직 없다.

## 6. 하지 않는 것

- 자동 발주·결제·오퍼·카탈로그 가격·공급자 연락·광고비 집행.
- robots.txt·약관이 막은 사이트의 자동 수집, 레지스트리 밖 호스트 호출, 리디렉트 따라가기.
- 외부 응답 원문 저장, 리뷰 작성자 등 개인정보 저장(개수만).
- 인용 검사를 통과하지 못한 모델 메모 저장, 모델이 점수를 바꾸는 것.

## 7. 상태

- 소스: 이 브랜치 커밋(병합 전). 배포·실키 호출은 `not_run`(키 발급 D3 대기). 검사는 `mocked`.
- 평가 2회차 서버 보강(H1 리스크 관문 필수 항목·H3 백테스트 생존 편향·H4 출처별 스냅샷 읽기·M1 격리 단위·M3 묶음 보정·M4 실행 시간 상한·잠금 갱신·M5 출시 뒤 결과·M6 소싱 후보 초안·성공률·손익 메모): `passed`·`mocked`. 화면이 새 GET 필드(`riskChecklists`·`calibration`·`launchOutcomes`·`anomalyFlags`)를 그리는 것은 화면 레인 몫이다.
- 평가 1회차 서버 보강(H4 하루 상한·H5 잠금 통일·H6 화면 응답 규모·M1 기준일·M8 검사 상수·M9 행 번호·① 자사 판매·② 신선도·이상치 격리·⑦ 리스크 검토·⑩ 니즈 초안·소싱 연결·⑪ 재시도·경보·주간 리포트·⑫ 승인 관문): `passed`·`mocked`. 자사 판매 시계열을 점수 입력에 쓰는 것, `ScoreCard.needsReview`를 붙이는 것, 재계산이 `sourcing`을 직접 보존하는 것은 분석 계층(`server-pipeline.ts`·`analytics/*`) 몫이다(서버는 재계산 뒤 연결을 되돌려 둔다).
